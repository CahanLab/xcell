# Changelog

All notable changes to xcell are documented in this file.
Format follows [Keep a Changelog](https://keepachangelog.com/).

## [Unreleased]

### Added
- **A Localize estimator that gives every cell its own spot, and a warning the default has earned (Analyze → Spatial → Localize).** Phase 1 made the failure measurable; this acts on what it measured. Two independent pieces.
  - **`injective` — best match solved as a set rather than one cell at a time.** `best_match` takes each cell's single best spot independently, so a spot that correlates well with everything — better recovered, less noisy — absorbs many cells. Optimal assignment maximizes total similarity subject to *distinct* spots, via `scipy.optimize.linear_sum_assignment`. On the E11.5 limb pair (2,683 cells, 9,773 spots): **2,683 distinct spots out of 2,683**, up from 1,522 for greedy, in about a second. The cost is a few percent of mean similarity.
  - **It is not better, it is elsewhere on the same frontier, and the UI says so.** Filling the tissue and carrying a gradient are the two ends of one trade-off. Measured on that pair: `weighted_mean` area **0.17** with the epidermis at **−0.16** — inverted — while any single-location estimator holds area **1.00** with the gradients gone. `injective` fixes pile-up, not placement; its axis correlations are greedy `best_match`'s to within noise. Presenting it as strictly better would be exactly the failure Phase 1 was built to prevent, so the panel, the guide and the Avoid list all state the trade rather than implying a winner.
  - **Off by default, and refused rather than fudged.** Injectivity asserts that the query's composition matches the tissue's; dissociation biases which cell types survive, so forcing one-to-one pushes over-represented types into locations they do not belong. It needs at least one spot per cell — the option is disabled when the query outnumbers the reference, and the same check runs in `prepare_localize` so an impossible run is a readable 400 rather than a background task that dies a minute in. It also materializes the whole query × reference similarity matrix, which the chunked top-k path never does, so there is an explicit size ceiling instead of an out-of-memory kill.
  - **The default's failure is now stated before the run, not after.** For every gene set curated in the Gene panel, `POST /api/localize/reference_geometry` asks the reference alone where the mean of that population's own positions falls. If the population forms a ring or hugs the tissue edge, that mean is a place none of its cells occupy — **the mean of a ring is its hole** — and `weighted mean` sends every query cell of the type there. On the limb reference: skin **0.88**, blood 0.70, cartilage 0.18, muscle 0.00. The modal names the ones at risk while the parameters are still being chosen.
  - **Two formulations were built and thrown away, both of which look right.** Counting how many of the cells around that mean are population *members* is correct in every case and far too noisy — 8 expected among 40 neighbours, so it fires on an ordinary scattered population about 1 seed in 60, and a user with a dozen gene sets would see a spurious warning most sessions. Scoring the *mean rank* of the tissue there fixes the variance and introduces a worse bug: it depends on how much tissue the population covers, saturating near 0.25 for a population covering a quarter of the reference, so the warning never fires. What ships compares the mean's distance from the population against the population's own spacing — scale-free, and blind to the background entirely.
  - **The real data corrected the design twice, and neither correction came from a test.** Taking a fixed top fraction as "the population" was silent on the very case it was built for: skin markers are detected in only 7% of limb spots, so the top 20% is mostly interior tissue with trace expression, the population fills the bud, and the risk reads 0.14 on a map already measured as inverted. Each fraction is now scored and the worst reported, with the fraction that produced it — at the top 2%, the epidermis proper, the same reference scores 0.88. Separately, averaging over 25 neighbours walks a quarter of the way around a thin band and hides its hole; at 5 a one-cell-wide perimeter scores 0.79 where 25 gives 0.38.
  - Backend: `injective_assignment` / `injective_feasibility` in `localize.py`, `mean_collapse_risk` in `localize_metrics.py`, `localize_reference_geometry` on the adaptor, `POST /api/localize/reference_geometry`. Frontend: `adviseParameters` moves to a pure, unit-tested `src/lib/localizeAdvice.ts` (17 cases, several asserting it stays *silent* — advice that fires on ordinary settings trains the user to ignore it).
- **Map quality — scoring a Localize map instead of eyeballing it (Analyze → Spatial → Localize).** On a real E11.5 mouse limb pair the default settings inverted the tissue's most basic anatomy — the epidermis, the outermost tissue in the embryo, was predicted into the middle of the bud — and nothing in the tool said so. The confidence score was working (mean 0.19 correctly reported that the matched neighbours were scattered), but "the map looks wrong" was not actionable: eight saved parameter variants existed on that dataset with no way to rank them. **Map quality** scores every predicted embedding in the query against the reference, so they can be compared rather than argued about.
  - **Four metrics, each answering a question a user actually asks.** *Spatial pattern fidelity* — does this cell type land where it lives? The headline number, and the one that catches the inversion: it goes **negative** when a type is placed where it is not, which is a different kind of wrong from merely weak. *Axis fidelity* — are the gradients real? Reported as "x of y possible" against what the reference itself achieves, because an attenuated correlation means nothing without its ceiling, and the direction is derived from the reference so the user never declares which way is distal. *Dispersion* — does the map fill the tissue, with cells pushed outside it counted separately, since a rescale can reach the right area by ejecting cells. *Occupancy* — distinct spots used, maximum on any one, and the effective number from the assignment entropy, which catches a better-recovered spot absorbing many cells even when the distinct count looks fine.
  - **Everything is rank-based, and not for style.** The reference is spot-resolved and the query is dissociated cells, so their expression scales are not comparable; and an estimator that shrinks the map changes the coordinate scale without changing what it claims. Ranking both sides makes every metric invariant to any monotone rescale — an affine rescale of the predictions provably cannot change a rank correlation, so a metric that moved under one would be measuring the wrong thing. That invariance is what makes maps from different settings comparable at all.
  - **One formulation had to be thrown away.** Comparing marker-*weighted* densities is the obvious approach and it is confounded: both maps then carry the same "where are there cells at all" signal, which dominates. Measured on synthetic geometry, two unrelated markers scored +0.33 and a fully inverted one only −0.07. Dividing the weighted sum by the cell count per bin isolates "is this marker high here", and the same three cases become +0.99 / −0.99 / ~0.
  - **What it says about the limb pair.** `weighted_mean` (k=50): area **0.15**, epidermis **−0.11** — inverted — but the proximodistal gradient largely intact (0.24 of a 0.34 ceiling). `best_match`: area **1.00**, epidermis **+0.29** — rim recovered — and the gradients gone (0.05 of 0.34). The two settings fail in opposite directions, which is the frontier the metrics exist to make visible: averaging preserves the gradient and collapses the extent; any single-location choice preserves the extent and keeps no gradient.
  - Backend: new pure module `backend/xcell/localize_metrics.py` (arrays in, dicts out, no adaptor import), `evaluate_localization_maps` on the adaptor, and `POST /api/localize/evaluate_map` which scores several embeddings per call because the numbers are only meaningful comparatively. A gene set with no genes present in both datasets is reported in `skipped_gene_sets` rather than failing the run.
- **Contour explains its parameters, and checks them against your data (Analyze → Spatial → Contour).** The tool asks for six numbers before it will do anything, and each one carried a tooltip that restated its label. Two of them were prefilled from a data-aware suggestion and then never mentioned again, so editing one left the sane range with nothing on screen to say so. The modal now raises advice against the *current* settings on both phases, and a collapsible **Show how to choose these** gives starting recipes per platform, the trade-offs, and an Avoid list.
  - **The coupling the form was hiding.** Sigma is measured in *grid pixels*, and a pixel is `extent / grid_res`, so the physical smoothing radius is `sigma × extent / grid_res` — **doubling the grid resolution halves the actual smoothing**. `suggest_smooth_sigma` solves for a radius of about two spot spacings, but the moment the grid is edited on its own that quietly stops holding and the bands break into speckle for reasons nothing on screen explains. Change the grid now and the tool says what the smoothing just became and what σ would restore it ("moving the grid to 80 changed the smoothing from 2 to 1.25 spot spacings without you touching σ; σ 1.7 would restore the original width").
  - **Everything is phrased in spot spacings**, not as disagreement with a suggested number the user never chose — under 1 the Gaussian never reaches the neighbouring spot; over about 6 it spans a whole zone and adjacent tissues merge; a grid many pixels finer than the sampling is interpolating detail rather than measuring it. That framing also keeps the thresholds honest: `suggest_grid_res` has a floor of 50, so on any dataset under ~2500 spots the suggestion *itself* puts two or three grid pixels between adjacent spots, and a naive threshold would fire on its own defaults.
  - **It reads the detected scale of `.X`** (from the existing `layer_scale` verdict on `/scanpy/layers`, no new endpoint) and says so when **Log transform** disagrees — off on raw counts, on over an already-logged matrix, or on over z-scored values where `log1p` of a negative is not a number the score can use. The route models default `log_transform` to `True` and the modal defaults it to `False`; rather than change a default that would alter results for anyone relying on it, the advice makes the current state legible.
  - **Review phase too:** a cutoff selecting no spots, or more than half of them (a module high everywhere wins overlaps by size rather than by signal), two modules broad enough that most assignments come from the neighbour vote rather than the contours under review, and a `profile_k` reaching past the local neighbourhood. Plus, before the run rather than after it: multi-set contouring without `X_pca`, and a gene set small enough that the module score is essentially one gene's spatial field.
  - The guide states the other thing the form hides: **bands are equal-width, not equal-count**. Thresholds are `linspace(0, vmax, levels + 2)[1:-1]`, so on a skewed field the top band holds few spots — the shape of the field, not weak expression — and more levels only subdivide the choice of cutoff.
  - Backend: `suggest_contour_params` additionally returns `n_spots`, `median_spacing` and `extent`, which `suggest_smooth_sigma` already computed and discarded. Frontend: pure `contourAdvice.ts` (`adviseContour`, `adviseModules`, `sectionColumnCandidates`), unit-tested directly — 30 cases, including one per rule staying *silent*, since advice that fires on its own defaults is noise.
- **UMAP and Leiden can run on any neighbor graph (Analyze → Cells → UMAP / Leiden).** Both read `obsp['connectivities']` and nothing else, so the spatial graph was unreachable and a Combine Neighbors result could only be used by *overwriting* the expression graph in place — losing it, and leaving no trace of which graph produced the current `X_umap`. Both now take a **kNN graph** picker listing every connectivity graph in the dataset, and name their output after it (`X_umap_spatial`, `leiden_spatial`), so an expression map and a spatially-informed one sit side by side. The name is editable and re-prefills when you change graph unless you have typed over it. The unlocked analysis is **spatial domain detection** — clustering spots by who they sit next to, which finds contiguous regions of tissue rather than cell types (measured on the bundled toy: 10 domains at 0.97 mean agreement among each spot's six nearest neighbours, against ~0.1 for random labels).
  - **It works on a dataset that has no PCA and no expression graph at all** — Visium plus Spatial Neighbors, which is precisely the case the feature exists for. Both tools listed `neighbors` as a prerequisite, meaning `obsp['connectivities']`; naming a graph explicitly supplies its own, so that gate is bypassed rather than blocking a run the backend now accepts.
  - **scanpy needed repairing to accept these graphs.** `sc.tl.umap` has no `obsp=` parameter — it reads `uns[neighbors_key]` — and neither graph xcell produces can be handed to it as it stands: squidpy's `uns['spatial_neighbors']` has no `params['method']`, which `tl.umap` reads unguarded (`KeyError`), and `combine_neighbor_graphs` writes only the matrix while `NeighborsView` requires `distances_key` to be *present* (the matrix it names is never read — UMAP uses connectivities only). The adaptor synthesizes a complete entry, starting from any real one pointing at that graph so squidpy's recorded `n_neighbors` survives into the export rather than being replaced by an invention, and deletes it in a `finally` so a failed run cannot leave a fabricated neighbors entry for the next tool to find. Leiden needs none of this; `sc.tl.leiden` takes `obsp=` directly.
  - **One silent side effect was worth the whole exercise.** With no representation named, scanpy falls through to `_get_pca_or_small_x`, which — when `X_pca` is absent and the dataset has more than 50 genes — **runs `sc.pp.pca` and writes `X_pca` + `uns['pca']` into the object**, behind a warning. That would put an embedding into the AnnData that no recorded step created, so the Analysis Record's exported notebook would not reproduce the state it claims to. Passing `use_rep='X'` takes the branch that simply reads `.X`, and costs nothing: for `method='umap'` the matrix is not what drives the layout. The recorded step carries the entry that was really installed, so the exported notebook avoids the same trap; verified by executing the emitted cells on a fresh AnnData and confirming identical names and no `X_pca` on either side.
  - Backend: `graph_key` / `key_added` on `run_umap`, `graph_key` on `run_leiden`, `_umap_neighbors_meta` for the synthesis, a `suffix` field on `/api/scanpy/neighbor_graphs` so the frontend and backend derive names from one rule. Both methods' cell-selection paths sliced a hardcoded `['connectivities', 'distances']`; they now slice the graph the run actually uses.
- **Localize — predict spatial coordinates for dissociated cells (Analyze → Spatial → Localize).** Load a spatial dataset into one slot and an scRNA-seq dataset into the other, and every cell in the scRNA-seq data gets a predicted position: its *k* nearest transcriptional neighbours among the spatially-resolved cells vote on where it came from. The result is a new embedding (`.obsm['X_spatial_pred']`), so the whole existing stack — colouring, contours, spatial neighbours, ligand-receptor — then applies to a dataset that never had coordinates. Parameters are all interpretable: *k*, the gene subset, the similarity metric, the expression transform, and how the neighbours' coordinates are combined. This is the first feature that spans two dataset slots.
  - **The failure mode it is built around.** Averaging the coordinates of *k* transcriptionally-similar cells is only meaningful if those cells are spatially co-located. A cell type dispersed through the tissue — immune cells, fibroblasts — has neighbours scattered everywhere, and their centroid lands in the middle of the tissue, possibly somewhere that type never occurs. A type sitting in two distant patches is worse: the mean lands squarely in the gap. Both produce a smooth, convincing, entirely wrong map, and nothing about the coordinate itself gives it away. So every prediction carries **two independent scores**, both written to `.obs` and neither optional: `_similarity` (does this cell resemble anything in the reference at all — a cell type absent from the spatial data is still placed *somewhere*) and `_confidence` (do its neighbours agree on a location — the weighted spatial spread of the *k* neighbours normalized by the reference tissue's own radius, so 1 means they sat on one spot and 0 means they were as scattered as the whole tissue). Cells below a chosen `min_confidence` get **NaN coordinates** rather than a fabricated point; the default places everything and flags it, because silently dropping cells is its own kind of lie.
  - **Aggregation.** `weighted_mean` (the classic estimator), `median` (robust to a few scattered neighbours), `best_match` (snaps to a real reference cell, so a prediction never lands somewhere the tissue does not exist) and `densest` — which averages only the tightest cluster among the neighbours. `densest` is the answer to bimodality: it lands the cell in one of the two patches rather than in the empty gap between them. It **cannot say which patch** — two patches sharing an expression program are indistinguishable to anything reading expression — and does not pretend to; on the bundled benchmark it picks correctly about half the time, which is why the default stays the mean and the confidence score (near zero for such cells either way) is what says not to trust the choice.
  - **Choosing which genes similarity is computed over.** A **Similarity basis** picker offers every shared gene, any boolean `.var` flag on the *reference* (`spatially_variable` from Spatial Autocorrelation, `highly_variable`, …), or any gene set curated in the Gene panel. The reference owns the choice because it is the dataset that can show which genes carry positional signal. The gene-overlap preview recomputes as you change it, so narrowing the basis immediately shows what it costs in shared genes. How much it helps depends on the panel: on whole-transcriptome data, restricting to spatially variable genes removes thousands of genes that say nothing about position; on an already-targeted panel, expect little change (measured on the bundled benchmark: 40 highly-variable genes score 32.7 against 33.0 for all 120).
  - **Guidance about the parameters, in the tool.** The panel raises warnings against the current selection rather than listing caveats nobody reads — `none` + `euclidean` across platforms (sequencing depth becomes the strongest signal), a *k* above a tenth of the reference (every prediction drifts to the tissue centre), `densest` with too few neighbours to cluster, `best_match` (where *k* no longer affects the coordinate, only the confidence score). A collapsible reference gives three concrete starting recipes and states each parameter's trade-off, including the one that matters most: a smoother map is what this method produces when it is failing, so tune against the accuracy check rather than against the picture.
  - **Cross-platform by default.** The transform is applied to each dataset *independently*, which is what removes platform-level per-gene capture efficiency: `zscore` (default), `rank` (Spearman-equivalent, robust to any monotone difference), `log1p`, `none`. Gene overlap is computed by **name** and reported with a severity band before anything runs — the same reasoning as the PySingleCellNet coverage check — and refused outright below ten shared genes, since a map from a handful of genes still looks smooth and means nothing. A multi-section reference is handled by assigning each cell the weighted-majority section among its neighbours and drawing coordinates only from that one, so a position is never averaged across the gap between cuts.
  - **Accuracy you can check before trusting it.** A **Check accuracy** button holds out a fifth of the *reference* and predicts it from the rest with the same parameters, where ground truth is exact. It reports median error next to **two baselines** — predicting the tissue centroid, and predicting at random — because an error reported alone is unfalsifiable: on a compact tissue the centroid baseline is deceptively strong, and the panel says so outright when the method fails to beat it. Also reported: the fraction landing within 5/10/25% of the tissue diameter, a structure correlation (do cells predicted near each other actually sit near each other?), a per-cell-type breakdown, and the correlation between confidence and actual error — the design's own falsification test, since a confidence score that does not predict error is decoration. The check is labelled as an upper bound, since both halves come from one platform and the real cross-platform mapping is worse.
  - **A benchmark with exact ground truth ships with it.** `toy_localize_spatial.h5ad` + `toy_localize_scrna.h5ad` (generator: `python -m xcell.data.generate_toy_localize`), a matched pair whose true coordinates are kept in `.obsm['spatial_true']`. The tissue is built to defeat the method: four region-restricted programs are the easy case, while `Immune` is dispersed with no positional signal, `Bipolar` sits in two distant patches sharing one program, and `Circulating` exists only in the query. The two files differ in depth, dropout and per-gene capture, so the transform matters the way it does across real platforms. Measured on it: median error **32.8** against a **66.7** centroid and **86.8** random baseline; per type, the four localizable programs land at 21–24 and the three unlocalizable ones at 64–79; confidence tracks error at r=**−0.66**; and of 900 query cells, **386** score below 0.2 confidence where 388 are unlocalizable by construction — the score identifies almost exactly the right cells.
  - Backend: new pure module `backend/xcell/localize.py` (projection, four aggregations, `evaluate_localization`, `cross_validate_localization`); `spatial_reference_bundle` on the reference adaptor and `prepare_localize` / `prepare_localize_cross_validation` / `evaluate_localization` on the query; `GET /localize/suggest` + `POST /localize/prepare` / `/cross_validate` / `/evaluate`. Frontend `LocalizeModal`. Because two datasets are involved, the reference exports plain arrays rather than letting a route reach into its AnnData.
- **Analysis record — export a GUI session as a runnable Jupyter notebook or Markdown (File → Analysis record…).** Reproducibility is the standing objection to GUI analysis: you click through thirty operations and nothing about that path is publishable, re-runnable, or legible six months later. Every mutating operation is now recorded — the load, its parameters, its result — and the record exports as a notebook whose code cells re-execute the analysis, or as a Markdown methods supplement. Steps carry the user's own annotations plus a generated one-line summary built from the real numbers (*"Leiden clustering at resolution 1.0 → 12 clusters in `.obs['leiden']`"*), and figures captured from the plot (**◧ Figure**) become inline outputs in the notebook and linked PNGs beside the Markdown.
  - **The document says how much of itself actually re-runs.** The tempting version of this feature emits a tidy notebook that *looks* authoritative; that version is worse than nothing, because a methods supplement describing an analysis nobody ran is a citation-grade error. So each step carries a **fidelity**: `exact` — the emitted line is the library call the adaptor really makes (`run_normalize_total` with no active selection literally executes `sc.pp.normalize_total(self.adata, **kwargs)`, which is why it earns the label); `xcell` — reproducible only by calling xcell's own Python API, which the notebook sets up by wrapping the AnnData in a `DataAdaptor`, including a runner for the two-phase `prepare_*` operations; `manual` — described in prose and not pretended to be code. The header states the split in numbers, and an action with no translation still exports as prose with its parameters rather than vanishing. A test scans `adaptor.py` for every `_log_action` name and fails if any lacks a translation, so a new operation cannot silently degrade an export.
  - **Operations that ran on a cell selection say so.** Ten adaptor methods accept `active_cell_indices` and none of them recorded it, so Leiden on a 4,000-cell lasso was logged indistinguishably from Leiden on all 40,000. The selection is now recorded (and preserved verbatim, up to 50,000 indices, in a `_selections.json` sidecar) and every affected step is flagged in the panel and in the exported document. We deliberately do **not** generate subset + write-back code: each of those methods has different write-back semantics — UMAP writes NaN for inactive cells, Leiden writes `'unassigned'`, `normalize_total` splices sparse data rows — and generated code that is subtly wrong is exactly the failure this feature exists to prevent. The emitted call runs on the whole dataset and says as much.
  - **Recording is always on; what you control is the report.** A record button users forget to press loses the analysis outright, and logging already cost nothing, so the recorder accumulates from load. **Start report here** marks where the story begins without discarding anything earlier.
  - **The record travels with the data.** It is written into `uns['xcell_analysis_record']` as a JSON string (h5ad copes badly with deeply nested heterogeneous dicts) minus figure payloads, so an exported `.h5ad` carries its own provenance and re-opening it continues the history rather than starting a second one. Export writes server-side into a folder you pick with the file browser — a notebook has to live next to the data to re-read it.
  - **Sixteen operations that recorded nothing now do:** label renames and merges, hand-painted annotation, QC metrics, differential expression, both gene-set scorers, the `.var`-side edits (gene renaming, boolean flags, per-pattern and per-species count sums, identifier swap), obs-derived embeddings, and the ligand-receptor analysis itself — `finalize_ligrec` logged only the `.obs` columns it wrote, never the radius, permutations or threshold that produced them. The load is recorded too, distinguishing h5ad / 10x h5 / 10x mtx / in-memory, so a dataset built in memory is reported as not reproducible instead of pretending a file exists.
  - Backend: new pure modules `backend/xcell/analysis_record.py` (the model and its `uns` round-trip), `codegen.py` (one `ActionSpec` per action: label, summary, code, fidelity) and `notebook_export.py` (nbformat-4 and Markdown emitters); `/api/record` routes for reading, annotating, marking and exporting. Frontend `AnalysisRecordPanel`, plus figure capture on the plot which re-renders the stored snapshot points into an offscreen 2D canvas — deck.gl does not set `preserveDrawingBuffer`, so reading back the live WebGL canvas is not reliable.
- **Cell type classification with PySingleCellNet (toolbar → Cell Typing).** An optional integration with [PySingleCellNet](https://github.com/CahanLab/PySingleCellNet), which classifies cells by voting a random forest over *top-scoring gene pairs* ("is gene A above gene B in this cell?"). Two tabs. **Classify** takes a pickled classifier, and before running anything reports what it is (classes, gene pairs, trees, training parameters) and — the part that matters — **how much of its gene set this dataset actually has**. PySCN reindexes a query onto the classifier's genes with `fill_value=0`, so missing genes silently become zeros and a badly-matched query still returns confident-looking scores; coverage is shown with a severity band (ok / warn / error) and the missing symbols listed. A pure `ACTB`/`Actb` casing mismatch is detected as such and offers a one-click case-insensitive match rather than reporting 0% overlap. **Train** builds a classifier from a categorical `.obs` column — balancing cells per type, normalizing, and selecting HVGs on a private copy, so the loaded dataset is never modified — writes the pickle, and hands it straight to the Classify tab. Both run as cancellable background tasks with live progress.
  - Results land in the slots xcell already knows how to draw: `<key>_class_argmax` (the call, a categorical whose colors come from the classifier's own `ctColors` via `uns['<column>_colors']`), `<key>_class_score` (the winning vote proportion, i.e. the call's confidence), and optionally `<key>_class_type` — **Singular** / **Ambiguous** / **None** / **Rand**, following PySCN's `categorize_classification` rules with self-calibrated per-class thresholds (`comp_ct_thresh`). PySCN splits the multi-class case into *Intermediate* and *Hybrid* using a cell-type relatedness graph xcell does not have, so those cells are reported as **Ambiguous** rather than guessed at. The full cells × classes score matrix goes to `.obsm['<key>_score']` and is registered in `uns['xcell_score_matrices']`, so the existing **◈ score matrix** pills in the Genes panel colour by any single class and the embedding picker can plot two classes against each other. The run is recorded in `uns['pyscn'][<key>]`; re-running under a different prefix keeps both results side by side.
  - **Training adapts to the scale the reference is already on.** Many public references are distributed *only* as log-normalized values, and running `normalize_total` + `log1p` over those again yields `log1p(scale(log1p(x)))`. Training now detects the source scale (via the expression-scale detection above) and applies only the preprocessing still owed — everything for raw counts, `log1p` alone for linear-normalized data, nothing for already-logged data — picking the HVG flavor to match, and never labelling a log-valued matrix as `counts` for `seurat_v3` to consume. A **Scale of that matrix** dropdown shows what was detected and overrides it, since detection is a heuristic; the result panel states exactly what was applied. A z-scored source is refused outright. Worth being precise about the blast radius, which is smaller than it looks: the top-scoring-pair features are *bit-identical* under a double log, because `normalize_total` and `log1p` are per-cell monotone and the transform only compares two genes within one cell (pinned by a test). What the double transform corrupts is gene *selection* — `rank_genes_groups`, the PCA/dendrogram used to find similar cell types, and HVG.
  - **The package is optional.** Nothing imports it at module scope; when it is absent the panel shows install instructions instead of failing, and *classifier inspection still works* (it only needs scikit-learn) so a classifier can be checked against the data before committing to the install. `pixi install -e pyscn` provides it reproducibly.
  - Two failure modes of the upstream library are handled rather than passed through. xcell narrows the query to exactly the classifier's genes before handing it over, so the dense intermediate PySCN builds is proportional to the classifier (a few hundred columns) rather than to the dataset — the difference between megabytes and tens of gigabytes on a large query — and prediction is chunked over cells. And because PySCN encodes each gene pair as the string `geneA_geneB` and decodes it with `split("_")`, **gene symbols containing an underscore cannot be represented**: training now excludes them and says how many, refuses with an explanation when too few remain, and loading a classifier trained on such symbols fails with a clear message instead of an opaque pandas `KeyError` at prediction time.
  - Backend: new module `backend/xcell/pyscn.py`, `pyscn_status` / `pyscn_inspect_classifier` / `prepare_pyscn_classify` / `prepare_pyscn_train` on the adaptor, and `GET /pyscn/status` + `POST /pyscn/inspect_classifier` + `/pyscn/classify` + `/pyscn/train` routes; frontend `PyscnModal`.
- **Expression scale detection — "is this layer raw counts or already normalized?"** Every readable matrix (`.X` and each `adata.layers` key) is now classified from its own values as **raw counts**, **normalized (linear)**, **log-normalized**, **log-transformed**, **scaled / z-scored**, or **binary**. Files arrive from collaborators and public repositories with no record of what was done to them, and guessing wrong is not cosmetic: `normalize_total` on already-normalized data is a no-op that looks fine, UCell ranks and PySCN's gene-pair transform assume a per-cell monotone scale, and z-scored input breaks anything expecting non-negative values. The signals, in the order they discriminate: negatives (only centering produces them), integrality (counts are integers), constant row sums (`normalize_total` fixes the library size), constant `expm1` row sums (the same check after undoing `log1p`, which identifies the scanpy-default scale), and dynamic range as a fallback for the common case where genes were subset after normalizing and the row-sum signal is gone. Alongside the inference it reports **recorded provenance**, which is fact rather than guess: `adata.uns['log1p']` from scanpy, the `counts` layer xcell snapshots at load time, and xcell's own `normalize_total` / `log1p` / `scale` / `smooth` history.
  - Surfaced unobtrusively: the verdict rides inline in the existing **Source** dropdown labels (`.X (default) — log-normalized`), and a 16px **ⓘ** opens a popover with the confidence level, the reasoning in plain language, the provenance, and the underlying statistics. The Source row now renders for single-`.X` datasets too, which need the answer just as much. The UCell and Cell Typing dialogs reuse the badge next to their layer pickers and warn outright when a z-scored layer is selected, since both are rank-based and would produce silently meaningless results.
  - Backend: new module `backend/xcell/layer_scale.py`; `list_layers()` attaches a `scale` block to each entry, so `GET /scanpy/layers` carries it with no new endpoint. Frontend `LayerScaleInfo`.
- **Score matrices written by other tools are readable.** `.obsm` entries stored as labelled pandas DataFrames — how PySingleCellNet writes `SCN_score`, among others — now expose their own column names to the schema, colouring, and embedding pickers, so an `.h5ad` classified elsewhere can be explored in xcell without conversion.
- **Ligand-Receptor spatial signaling (Analyze → Spatial → Ligand-Receptor).** A from-scratch NumPy/SciPy port of the core LRscore + permutation statistics of [CytoSignal](https://github.com/welch-lab/CytoSignal) (velocity/dynamics omitted). For each cell and each L-R interaction it imputes ligand expression over a spatial neighborhood — a Gaussian ε-ball for **diffusion**-dependent (secreted) ligands, direct **Delaunay** neighbors for **contact**-dependent (membrane) ligands — multiplies it by the cell's own receptor, spatially smooths the score, and tests significance against a spatial permutation null (shuffle the ligand neighborhood, keep each cell's receptor) with a BH-adjusted per-cell p-value. The tool ranks interactions by number of significant cells; pick any to write its per-cell score as a continuous `.obs` column (`LR_<ligand>_to_<receptor>`) and visualize it on the embedding. Parameters (diffusion radius, permutations, min cells/gene) are prefilled from the data with inline tips, and the run shows a **live progress bar** (permutation count, % and elapsed/ETA). The full per-cell score + significance matrices are persisted to the dataset (**`.obsm['lrscore']`** / `['lrscore_significant']`, with metadata in `.uns['lrscore']`) — `.obsm` is the correct cell×interaction home (`.obsp` is cell×cell). Because results persist, **re-opening the tool restores the ranked table so you can visualize different interactions without re-running**; only changing scoring parameters (radius, permutations, …) requires a recompute. **Section-aware**: an optional Section column keeps neighborhoods *and the permutation null* within section (no signaling across the gap between tissue sections). **Gene subset**: optionally restrict eligible genes to a boolean `.var` column (e.g. `highly_variable` / `spatially_variable`); off by default. The scoring engine reduces the expression matrix to just the genes used by the candidate pairs and computes the (permutation-invariant) receptor side once — roughly a **35×** speedup on a 2,000-gene panel (and more for whole-transcriptome data). It builds its own Gaussian/Delaunay neighbor graphs each run and does not reuse the Spatial Neighbors graph. Ships a bundled ligand-receptor database (`backend/xcell/data/lr_pairs.csv`, 2508 pairs distilled from CellPhoneDB v5 with the diffusion/contact split and multi-subunit complexes preserved; rebuild with `python -m xcell.data.build_lr_db`). The database uses human (UPPERCASE) symbols but is matched **case-insensitively** to the dataset's gene names, so it works on mouse data (`Pdgfb` → `PDGFB`) — mirroring CytoSignal's uppercase-match; written columns use the dataset's actual gene names. (This is a heuristic; a proper mouse→human ortholog table is planned — see `docs/ROADMAP.md`.) and a synthetic test dataset with known planted signaling (`toy_spatial_ligrec.h5ad`; generator `generate_toy_ligrec.py`). Backend: new pure module `backend/xcell/ligrec.py`, two-phase `prepare_ligrec` (cancellable background task) / `finalize_ligrec` on the adaptor, `GET /scanpy/ligrec/suggest` + `POST /scanpy/ligrec/prepare` + `/finalize` routes; frontend `LigRecModal`.
- **Refine a category with subcluster labels (Cells → Categorical → ⋯ → Refine with subcluster labels…).** After masking some cells and subclustering the rest (which leaves the masked cells `unassigned` in a new column), fold those subcluster labels back into a parent annotation: every cell with a real subcluster label takes it (optionally renamed — prefix with the parent label, e.g. `Mesen.0`, use as-is, or a custom prefix), while cells the subcluster left unassigned keep their parent label. Writes a new column or overwrites the parent in place; surviving parent labels keep their colors. Backend: `transfer_obs_labels` on the adaptor + `POST /obs/transfer_labels`; frontend `TransferLabelsModal`.
- **Categorical labels overlaid on the embedding (Cells → Categorical → ⋯ → Show labels on plot).** Toggle category names rendered at each cluster's centroid (robust median position) directly on the embedding, with a dark halo for legibility. Turning it on also colors by that column so the labels match the clusters.

### Fixed
- **Localize could never pick a spatial reference.** The modal seeded its reference slot with the literal string `'secondary'` and asked the server for the list of usable slots *with that guess attached*. But the list only comes back from a call naming a **valid** reference, and both natural arrangements return 400 — `?reference=secondary` when the coordinates are in primary ("no spatial coordinates"), and `?reference=secondary&dataset=secondary` when the user makes the scRNA-seq active ("the reference must be a different dataset"). Both 400s were swallowed deliberately, since a slot without coordinates is a normal state rather than an error, and the handler returned before `setRefs` — so the list stayed empty, the tool reported *"No loaded dataset has spatial coordinates"* while a perfectly good one was loaded, and the picker that would have corrected the guess was itself built from the list that never arrived. A bootstrap deadlock: switching the active dataset produced a different 400 and the same message. The slot list is now fetched with no reference at all, which the route answers unconditionally (it builds the list before validating a reference), so the picker always populates.
  - **Roles no longer depend on which dataset is active.** Localize is the one feature spanning two slots, and it inferred the query from the active one — punishing the obvious workflow of loading the spatial data, looking at it, and then trying to map onto it. The dataset holding coordinates is now the reference and the other is the query, whichever is being viewed. The modal states both, plus which dataset the predictions get written into, and offers a swap when both carry coordinates. The role logic is a pure function (`lib/localizeRoles.ts`) with its own tests, including one asserting the answer does not move when the active slot changes.
- **Neighbors on a cell selection failed for every dataset.** `run_neighbors` builds a throwaway AnnData holding only the selected cells' `.obsm` representation, deliberately with no `.X`. scanpy's `use_rep=None` default resolves the representation from `adata.n_vars`, which on that object is 0, so it fell through to `.X` and raised on `None`. The whole sequence a user performs — lasso a subset, PCA, Neighbors, Leiden — could not complete. The representation is now named explicitly.
- **An embedding containing NaN returned a 500.** NaN is a legitimate value there: `run_pca` and `run_umap` on a cell selection leave inactive cells NaN, and Localize leaves unplaceable cells NaN rather than fabricating a position. But starlette serializes strictly, so `GET /api/embedding/<name>` raised *"Out of range float values are not JSON compliant"* and the result of a subset UMAP could not be displayed at all. Non-finite coordinates now cross the wire as `null`.
- **Figure builder: highlighted cells no longer obscured by overlapping low-expression cells.** When a figure panel colored cells by expression (or a numeric/bivariate source) *and* the highlight overlay was on, an overlapping non-highlighted zero/low-expression cell could be drawn over a highlighted cell and hide its color — visible when zoomed out (e.g. purple min-expression spots covering brown cartilage-highlighted spots). `FigurePanel` ordered cells by expression value only; it now applies a second stable sort by max highlight weight (matching the main Embedding view), so highlighted cells render on top. Applies to the PNG export too.

When the loaded h5ad had a populated `adata.raw` with a larger gene set than `adata.X` (e.g., a curated dataset where `.X` was trimmed but `.raw` kept the full transcriptome), scanpy's default `use_raw=True` silently pulled marker names from `.raw.var_names`. Those names were unreachable for visualization (which reads from `.X`), and worse, the marker list could include genes the user had explicitly removed via `exclude_genes`. Now uses `use_raw=False`, matching the two-group diff-exp path which was already correct. Existing saved marker gene sets still contain the stale names; re-run Compare Cells to get a clean set.
- Pass `activeSlot` explicitly to `runMarkerGenes`, `useDiffExp.runComparison`, and `ScanpyModal`'s Compare-Cells diff-exp call. (Defensive — `appendDataset` already auto-defaults to the store's `activeSlot`, but the explicit thread makes slot intent obvious at the call site.)
- Select → Lasso could silently stop drawing after switching between Lasso and Polygon. `handleMouseDown`'s `useCallback` deps array omitted `selectionTool`, so once the user had selected Polygon and then triggered any other dep change (toggling interactionMode, etc.), the handler stayed bound to a stale closure with `'polygon'` captured and returned early on every drag — leaving the user in "lasso mode" by the toolbar but with dragging doing nothing.
- Cell selection from Contourize annotations (and any other categorical `.obs` column with non-string category values) now works. Clicking a contour level in the Cells panel selects the corresponding cells; the same fix unblocks the "Compare Cells" picker in the Scanpy modal for these columns. The bug was a wire-format mismatch — `/api/obs/{col}` returned raw float categories while `/api/obs/summary/{col}` stringified them, so the frontend's `indexOf` lookup never matched.
- Segmented-line draw tool: the first segment is now drawn on the first try. Previously, selecting "Segmented Line" from the Draw dropdown after already being in draw mode left `handleMouseDown` / `handleMouseUp` bound to a stale `drawTool` closure (they didn't list `drawTool` as a `useCallback` dep), so the first click followed the pencil code path, cleared the line points, and the segmented line never accumulated points until the user toggled Draw off and on.
- Line association (clustering off): the results modal now renders the significant genes as collapsible Increasing/Decreasing cards, shows filter controls (min R², min amplitude, max FDR) for them, and enables "Add to Gene Sets" — previously the modal showed "No significant genes found" and the button was silently disabled because the old list-view path only handled module output.
- Spatial Autocorrelation no longer errors with `Expected n_perms to be positive, found 0` when Permutations is set to 0. The modal already documented 0 as the "analytical only" setting; the backend now translates `n_perms=0` to `None` (squidpy's analytical-only path) before dispatch.

### Added
- **In-plot `Source:` layer dropdown for visualization**. A new dropdown appears in the bottom-left of the main scatter view (alongside the Embedding selector) whenever the active dataset has any non-X layer (typically after running Preprocess → Smooth). Picking a layer reroutes single-gene, gene-set, and bivariate coloring through that layer so you can visually inspect smoothed (or any other layered) values without modifying `.X`. The selection is per-dataset, persists for the session, and falls back to `.X (default)` if the chosen layer disappears (e.g. after reloading the dataset). Single-gene, multi-gene aggregation, and bivariate expression endpoints all gained an optional `layer` argument that overrides `transform` when set.
- **kNN smoothing in Preprocess → Smooth**. New Scanpy modal entry that smooths gene expression over any cell-cell kNN graph in `obsp` (Spatial Neighbors, Cell Neighbors, or a Combined graph). Algorithm: one or more iterations of `S ← D⁻¹·(A + α·I)·X` where α is the self-loop weight. The result is written to `adata.layers[output_layer]` (default `smoothed`) — `.X` is **not** modified. To use the smoothed values, pick the new layer from the `Source matrix` dropdown that now appears on Gene PCA, Gene Neighbors, and the Cluster Genes modal. Picking DBSCAN replaces the K input with two new inputs: `eps` (neighbor radius in correlation-distance space, default 0.3 — i.e. genes are considered neighbors when their Pearson correlation is at least 0.7) and `min_samples` (minimum genes within `eps` for a gene to seed a cluster, default 3). Unlike K-based methods, DBSCAN discovers the number of clusters from the data; genes that fail the density threshold are returned as a trailing "noise" sub-cluster.
