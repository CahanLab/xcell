# Changelog

All notable changes to xcell are documented in this file.
Format follows [Keep a Changelog](https://keepachangelog.com/).

## [Unreleased]

### Added
- **Highly variable genes, per data split (Analyze → Preprocess → Highly Variable Genes → "Detect within groups of").** Pooled HVG detection on a multi-sample dataset finds genes that vary *between* samples as readily as genes that vary within them, so a batch effect scores as biology. Point this at a categorical `.obs` column — sample, section, donor — and detection runs inside each group separately, writing `highly_variable__<group>` per group, with optional **union** (variable in any group) and **intersection** (variable in every group) columns. On three real E11.5 hindlimb sections: 4,000 HVGs each, **union 7,530, intersection 1,030** — only a quarter of each section's variable genes are variable in all three, which is the number that should decide whether you feed pooled HVGs into a multi-sample analysis. The intersection is the conservative input for NMF meta-programs; the union is the inclusive one for integration.
  - **The pooled `highly_variable` column is never touched by a split run**, and no pooled column is invented if none existed — every gene-subset dropdown in xcell points at that name, and quietly redefining it would change what unrelated analyses mean. The new columns appear alongside it in the Gene Panel's `.var columns` list, each one materializable as a gene set.
  - Groups below `min_cells_per_group` (default 10) are skipped and named in the result rather than contributing a noisy answer; `.obs` categories no cell uses any more are ignored; and `subset=True` together with a split is refused outright, since there is no honest single gene set to subset to — run the split, then subset on the union or intersection.
  - The result says what happened instead of "Completed successfully": *"HVGs per section: A 4,000, B 4,000, C 4,000 · union 7,530, intersection 1,030. Pooled highly_variable left unchanged."*

### Fixed
- **New boolean `.var` columns appear without a page reload.** The Gene Panel's `.var columns` list fetched once on mount and never again, so any column written after load — highly variable genes, spatial autocorrelation, Add boolean column — stayed invisible until the tab was reloaded. It now re-fetches whenever the schema is replaced, which is the refresh every one of those operations already triggers.
- **Combine: choose which columns survive, and what happens to a collision (File → Combine datasets…).** Combining used to keep whatever `.obs` columns every input happened to share, merged into one column each, and take `.var` from the first dataset — silently. The dangerous case is a name collision that is **not** a value collision: two datasets each carrying `seurat_clusters` from *independent* clusterings, where cluster 3 in one has nothing to do with cluster 3 in the other. Pooling those into one column invents a comparison nobody made. Every `.obs` and `.var` column is now listed before you commit, with which datasets carry it and what will happen to it: **one column** (values pooled), **one per dataset** (`name__label`, empty for the other datasets' cells), or **drop**. Verified on two real E11.5 limb sections — hindlimb and forelimb, 71,444 cells combined — where the picker kept `seurat_clusters` and `SCT_snn_res.0.2` apart as `__hind`/`__fore` while merging `nCount_RNA`, `percent.mt` and `log_umi`, exactly as it should.
  - **The defaults are the safe reading, and they say why.** A per-cell measurement means the same thing in every dataset, so it merges; a categorical, a string, or a low-cardinality integer (≤50 distinct values — clusters stored as ints are still clusters) does not, so it stays apart. A column only one dataset has can't collide, so it merges under its own name. Each suggestion carries the sentence explaining it, shown on hover, and any column you move off its suggestion is outlined in amber.
  - **`.var` is decided by comparing values, not guessing.** Genes are the intersection, so the same column in two datasets annotates the *same* genes — which means xcell can just check. Identical everywhere (`gene_symbol`, `name`) → one copy; disagreeing (`highly_variable`, `moranI`) → one per dataset. The comparison is made over the shared genes only, since the rest are dropped by the combine anyway and disagreement outside the intersection is not a reason to split a column.
  - **Reading the columns does not read the matrices.** `POST /api/combine/columns` opens each h5ad backed and takes `.obs`/`.var` alone — 0.25 s for a 47,272 × 36,596 and a 24,172 × 12,236 dataset, so the picker is populated before you have finished reading the file list.
  - Split names never overwrite an existing column (a dataset that already has `x__A` keeps it; the split of `x` becomes `x__A_1`), `sample` is always written whatever the policy says, and the resolved policy — including every default xcell filled in — is recorded in `uns['xcell_combine']`, so the combined object says what was done to it. A policy naming a column no input has is a 400 rather than a silent no-op, because a typo that quietly drops a column is how you lose one without noticing.
- **NMF meta-programs: the gene programs that recur across samples (Analyze → Genes → NMF Meta-Programs).** The multi-sample half of [GeneNMF](https://github.com/carmonalab/GeneNMF) — `multiNMF` + `getMetaPrograms`. A single factorization cannot tell a real gene program from a batch effect, because it only ever saw one pooled matrix. This factorizes **each sample separately at every rank in a sweep** (default k=4–9), then clusters all the resulting programs by gene-weight similarity into consensus meta-programs, and scores each by **sample coverage** — how many samples it turned up in independently. On three real E11.5 hindlimb sections, 3 samples × 6 ranks = **117 factorizations in 1.9 s**, consolidated into 8 meta-programs: clean primitive erythroid (*Hbb-bh1/Hba-x/Slc25a37/Slc4a1/Hemgn*), ECM (*Col1a1/Col1a2/Postn/Lum/Dcn*), chondro-myogenic (*Sox9/Col2a1/Myog/Tnnt1*), and a distal *Hoxd11/Hoxd13/Grem1/Cyp26b1/Hand2/Lmx1b* program at 1/3 coverage — present in one section only, because the sections cut at different proximodistal levels. Each meta-program becomes a gene set plus a per-cell score in `obsm[key]`, registered as a score matrix so it colors like any pill; "Save all as gene sets" sends them to the Gene Panel. `POST /api/gene_nmf/meta/run` (202 + task), `GET /api/gene_nmf/meta/{result,runs,columns}`; 51 backend tests.
  - **A similarity heatmap that shows whether a consensus is real.** GeneNMF's `plotMetaPrograms`: every program against every other in dendrogram leaf order, each meta-program outlined as a block on the diagonal (canvas, so 117×117 renders instantly). A bright tight block is a genuine consensus; a dim one that bleeds into its neighbours is not — and the run's **silhouette** says the same thing numerically. On the limb data MP6 came back at silhouette **−0.05**, and the heatmap shows exactly why: a diffuse middle region where 30 programs cluster only because they had nowhere else to go. The UI labels that meta-program as a leftover cluster rather than pretending it is a finding. A **composition** tab counts each sample's programs per meta-program, so a row concentrated in one column reads as sample-specific at a glance.
  - **These defaults are the opposite of the single-sample tool's, and the measurement is why.** The single-sample path had to drop `specificity_weight` from GeneNMF's 5.0 to 1.0 because on one factorization the exponent piles a program's whole mass on one gene. That reasoning does **not** carry over: the meta-program consensus averages gene weights across every program in a cluster *before* the cutoff, which is precisely the smoothing the single-sample path lacks. So 5.0 survives here — but only paired with `weight_explained` raised 0.5 → **0.8**, since after weighting the surviving genes hold most of the mass. Measured across the full grid on three real sections: `(5.0, 0.5)` kills two of eight meta-programs and leaves the rest holding ~7 genes; `(5.0, 0.8)` keeps all eight at usable size with the best marker purity of any setting tried (0.72 against 0.56 at spec 1.0). Full grid: `docs/measurements/2026-08-19-gene-nmf-metaprogram-defaults.md`.
  - **Specificity is scored within a factorization, not across the study** — "how exclusive is this gene among *this* model's own factors". Pooling would make a gene's score depend on how many samples happened to be included, penalizing exactly the recurrent programs the tool exists to find, and penalizing them harder with every sample added. Likewise the consensus takes an **outlier-trimmed** mean across a cluster's programs, so one runaway program cannot carry a gene into the meta-program (3σ trimming can only fire at ≥12 programs per cluster, since max |z| is (n−1)/√n — the tests pin both rules where the planted fixture cannot reach them).
  - Empty `.obs` categories are ignored, samples below `min_cells` are skipped and reported by name, and a rank larger than a sample's cell or gene count is dropped rather than failing the whole sweep.
- **NMF gene programs: the overlapping states clustering can't separate (Analyze → Genes → NMF Programs).** Gene clustering partitions — one gene, one module, one cell, one cluster — which is the wrong shape for cycling, hypoxia or interferon response, states that ride *on top of* cell identity and share genes with it. This factorizes expression into `k` additive non-negative programs (`X ≈ H · Wᵀ`): a gene can carry weight in several programs, and each cell mixes them. Each program comes back as a ranked gene set **and** a per-cell usage score written to `obsm[key]` and registered as a score matrix, so a program is colorable as a pill exactly like a UCell score, and the matrix doubles as a k-dimensional embedding. "Save all as gene sets" drops the programs into the Gene Panel as a folder, ready for scoring, contouring or spatial work. Gene loadings persist to `varm[key_loadings]` the way PCA stores `varm['PCs']`; the full run (params, gene sets, weights, metrics) goes to `uns['xcell_gene_nmf'][key]` as plain dicts so it survives an h5ad round trip, and reopening the tool shows the stored run rather than recomputing. A Python port of the single-sample path of [GeneNMF](https://github.com/carmonalab/GeneNMF) (Andreatta & Carmona) — `runNMF` + `getNMFgenes` — in `backend/xcell/gene_nmf.py`, pure NumPy/SciPy, 34 tests. Verified in the browser on a real 24,172-cell × 12,236-gene E11.5 hindlimb section: at k=12 it recovers the distal *Hoxd13/Hoxd11/Grem1/Cyp26b1* domain, a *Sox9/Col2a1/Shox2* chondrogenic condensation, *Col1a1/Col1a2/Postn* connective tissue, a *Mki67/Cenpe/Birc5* cell-cycle program, primitive erythroid *Hba/Hbb*, and proximal *Meis1/Pbx1/Hoxc10*.
  - **It is roughly as fast as the C++ it is ported from.** The kernel is fast-HALS (Cichocki & Phan), and its two sparse products per iteration are ~95% of the runtime — SciPy releases the GIL inside them, so they are split across a thread pool over disjoint row blocks: **250k cells × 2k genes at k=20 in 8.8s**, against 48s for scikit-learn's `mu` and 377s for its default `cd` solver, at an equal or better residual (on the real limb data, 0.90687 vs sklearn `cd`'s 0.90670, in 2.5s vs 6.5s). Row blocking is exact rather than approximate — the same rows reduce in the same order whatever the thread count — so a run is reproducible bit-for-bit across machines, which a seeded factorization has to be. Sparse input is never densified; a 250k-cell matrix would be 4 GB dense.
  - **The scaling convention is load-bearing, not cosmetic.** Output follows RcppML's L1 diagonalization (`A ≈ W·diag(d)·H`, columns of `W` on the unit simplex, factors sorted by decreasing weight) because the gene-selection step compares each gene's loading *across* programs — an unnormalized factor would look artificially specific and hijack every program.
  - **The specificity weight defaults to 1.0, where GeneNMF uses 5.0**, and that difference is the whole feature working or not. The weighting scores each gene by `spec^w`, where `spec` is the largest share any one program takes of that gene's loading. On real data almost nothing is exclusive — measured specificity percentiles on the limb run were `[0.16, 0.21, 0.27, 0.36, 0.57]` — so at `w=5` the spread becomes ~600×, one gene ends up holding 60–98% of each program, and the cumulative-weight cutoff then keeps *nothing*: **4 of 12 programs survived, median 4 genes**. GeneNMF gets away with 5 because it only ever applies this to the *averaged* consensus of many programs (`getMetaPrograms`), which smooths the distribution first; the single-sample path has no such averaging. At `w=1`, 11–12 of 12 survive and the programs are visibly sharper than with no weighting at all (the distal factor leads with *Hoxd13/Hoxd11* rather than *Stip1/Sulf2*). Measurements and the full sweep: `docs/measurements/2026-08-19-gene-nmf-specificity-weight.md`.
  - **The source transform follows the layer's detected scale.** Every other gene-expression path in xcell defaults to normalize_total + log1p, which on a matrix that is already logged silently factorizes `log(1 + log(1 + counts))` — and NMF is more sensitive to that than coloring is, because the extra compression flattens exactly the high-expression differences the factors are built from. The tool reads the scale xcell already detects and picks the default from it, saying so inline ("This matrix is already on a log scale, so it is fed to NMF as-is"); a raw counts layer still gets log1p. Pure, tested module (`src/lib/nmfTransform.ts`, 9 cases).
  - **Multi-sample meta-programs (`multiNMF`/`getMetaPrograms`) are deliberately not here yet** — that is GeneNMF's other half, for finding programs recurrent across samples and across `k`, and it is worth doing only once the single-sample programs prove useful on real data.
- **Combine accepts every format Load does (File → Combine datasets…).** Combine used to demand `.h5ad` of every input while File → Load happily opened 10x `.h5`, Visium HD `feature_slice.h5`, Seurat `.rds`, 10x CellRanger matrix folders, and GEO-style `*_matrix.mtx(.gz)` file trios — so combining a fresh CellRanger run with an existing h5ad meant a manual conversion first. The constructor's format-sniffing now lives in one shared `load_dataset_file()` used by both paths, so **every loadable format combines**, in any mixture, with the same spatial-vs-concat behavior as before. `.rds` inputs go through the same R-based conversion as Load. Default `sample` labels are the bare dataset name (folder name, trio prefix, or filename without extension — `demoB.h5` → `demoB`). The file picker in Combine mode now accepts all of these too, and the 8 new backend tests build real 10x `.h5` and matrix-folder fixtures to pin the loader (`combine_h5ads` is now honestly named `combine_datasets`). Verified in the browser by combining an `.h5ad` with a CellRanger `.h5` into one 500-cell dataset.
- **Cell-type neighborhoods: who lives next to whom, and is it more than chance? (Analyze → Spatial → Neighborhood).** For a chosen categorical column (clusters, cell types), builds a spatial kNN graph (default k=10, Schürch-style windows; radius mode available), computes each cell's **neighbor-type fractions**, and tests every pair of types for co-location against a label-shuffling permutation null (histoCAT / squidpy `nhood_enrichment`-style, so enrichment can't be driven by a type merely being abundant) — z-scores, empirical two-sided p-values, and BH q-values, 1000 permutations in seconds even on large data (O(edges) pair-counting per permutation). Results render as a **types × types heatmap** with two views: *Enrichment (z)* — dark-neutral at z=0, coral = together more than chance, blue = less, dot = q < 0.05 — and *Composition* — what fraction of a type's neighbors each other type is (rows sum to 100%; directional, so an infiltrating type reads differently from its host). Hover any cell for z, q, observed vs expected %, and pair counts; axis swatches reuse the exact cluster colors from the scatter plot. Per-cell fractions persist to `obsm['neighborhood_composition']` and register as a score matrix, so *"fraction of muscle in this cell's neighborhood"* becomes a colorable pill like any score — the intended workflow for annotating ambiguous mesenchymal clusters by company kept. With a section column, edges never cross sections and labels shuffle within them. Pure module (`backend/xcell/neighborhood.py`, 13 tests with a planted checkerboard geometry whose answer is known), adaptor + routes (12 tests), pure viz helpers (`src/lib/neighborhoodViz.ts`, 11 cases); full flow verified in the browser on the 6-type toy dataset, including prior-result reuse on reopen.
- **Compare: two embeddings of the same dataset, side by side (◫ Compare in the toolbar).** One dataset, two geometries: the tissue on the left, the expression manifold on the right — or any pair of embeddings, each pane with its own camera and its own embedding picker. The second pane defaults to the complement of what you're looking at (spatial shown → UMAP offered, and vice versa). **Selection is one selection**: lasso a cluster in the UMAP pane and those same cells light up at their tissue positions in the spatial pane, and the other way round — verified in the browser with a 211-cell lasso crossing panes. Coloring, expression overlays, and highlights are shared the same way, because the cells are the same cells. The µm scale bar knows which pane shows real coordinates and appears only there. Draw and Adjust act on the first pane's embedding and are inert in the second — a line drawn on a UMAP must never render on the tissue. Distinct from the existing dual-dataset Split, which shows two *datasets*; Compare shows one dataset twice. The default-companion choice is a pure, tested module (`src/lib/pickSecondEmbedding.ts`, 4 cases).
- **Combine works on any datasets that share genes, not only spatial sections (File → Combine datasets…).** The combiner used to demand `obsm['X_spatial']` of every input — stricter than the rest of the app, which also accepts the `spatial` convention and an explicit `uns['xcell_spatial_key']` — and refused everything else. It now chooses by what the inputs carry: **all spatial** → the existing side-by-side section layout; **anything else** → plain row concatenation with no geometry invented, keeping the `.obsm` arrays every input shares (a common `X_pca`, say) so the combined dataset opens with a usable view instead of a blank one. Either way: gene intersection, a `sample` categorical column, collision-safe cell names, and `uns['xcell_combine']` recording the mode and labels. Endpoint is now `POST /api/combine` (`/api/combine_spatial` remains as an alias); the previously untested combiner gained 7 backend tests pinning both modes, the widened spatial detection, gene intersection, and the mixed-input case (which concatenates rather than pretending geometry).
- **A µm scale bar for spatial data (Display → Scale Bar).** The h5ad format carries no units — Curio Seeker writes µm, plain Visium writes full-res image pixels, a Localize map inherits its reference — so xcell asks rather than guesses: **Display → "µm per coordinate unit"** declares the physical size of one unit of the dataset's spatial coordinates (for Curio Seeker and Visium HD, enter 1), stored per dataset in `uns['xcell_spatial_scale']` so it survives export and reload. Once known, a bar renders bottom-right over the plot: always a round physical length (1/2/5 × 10ⁿ µm, labeled in µm or mm), resized as you zoom. It appears **only on the designated spatial embedding** — a UMAP has no physical scale, and neither does a coordinate array that merely looks spatial. **Visium HD datasets need no setup**: the loader builds its coordinates in µm and records `bin_size_um`, which is recognized automatically. Bar sizing is a pure, tested module (`src/lib/scaleBar.ts`, 4 cases); the setting round-trips through `GET/PUT /api/spatial_scale` (10 backend cases) and lands in the analysis record, since every µm in an exported figure means what this setting says.
- **Filter Cells shows the distributions it thresholds (Analyze → Preprocess → Filter Cells).** Two histograms — total counts per cell and genes per cell — appear above the numeric inputs, with draggable red cutoffs bound to the same four thresholds, a `log₁₀(1+x)` axis toggle (on by default; count distributions are unreadable linear), axis labels in data units either way, and a live *"876 of 1,000 cells pass the current thresholds"* line computed with exactly the backend's mask semantics (inclusive bounds, AND of everything set). Dragging a cutoff to the axis end clears that threshold. After a run the histograms refetch, so what you see is always the current dataset. Per-cell metrics come from a new `GET /api/scanpy/filter_cells/qc`; mapping and pass-count logic are a pure, tested module (`src/lib/filterCellsQc.ts`, 7 cases).
  - **Combining thresholds used to be an error, and now works.** `sc.pp.filter_cells` accepts exactly one threshold per call, and the adaptor passed everything to one call — so the shipped default (`Min genes` = 25) plus *any* other threshold was a 400: *"Only provide one of the optional parameters…"*. The adaptor now computes the keep-mask itself (same inclusive semantics scanpy applies, pinned by a test against scanpy's own result) and the exported notebook emits one `sc.pp.filter_cells` call per threshold, which is what makes those sequential calls both runnable and equivalent.

### Changed
- **UMAP and Leiden preselect the expression kNN graph (Analyze → Cells).** The kNN-graph dropdown used to sit on an implicit empty option labeled "Expression neighbors (default)", which named no actual graph and, on datasets carrying `obsp['connectivities']` without a `uns['neighbors']` entry (h5ads made elsewhere), failed the prerequisite check outright. When the expression graph exists it is now preselected by key, so the dropdown says exactly what will run — `Expression neighbors (connectivities, 21,198 edges)` — and the run goes through the explicit-graph path that works regardless of `uns`. Output names are unchanged (`X_umap`, `leiden`): the expression graph carries no suffix. A hand-made choice, including clearing back to the empty option (now honestly labeled "Dataset default graph"), is never overridden. Spatial-only datasets are left alone — silently clustering the spatial graph would answer a different question. Decision logic is a pure, tested module (`src/lib/graphChoice.ts`, 4 cases).
- **File → Export writes where you choose.** Every export streamed a browser download under a fixed name, so an h5ad landed in Downloads as `xcell_export.h5ad` whatever dataset it came from — export three variants and you had `xcell_export.h5ad`, `xcell_export (1).h5ad` and `xcell_export (2).h5ad` with no way to tell them apart. You now pick the folder and the name, and xcell writes the file there. Verified end to end: a real export reported `Wrote /Users/pcahan/Downloads/toy_spatial_xcell.h5ad (672.6 kB)` and read back in Python at the right shape with its annotation columns intact.
  - **The name is proposed from the dataset, not from a constant.** `toy_spatial.h5ad` offers `toy_spatial_xcell.h5ad`, `toy_spatial_annotations.tsv`, `toy_spatial_gene_sets.json`, so two exports of different datasets cannot collide by default.
  - **An overwrite is visible before the button, not after it.** The picker watches the entries of the folder it is showing, so a name that already exists there says so in amber while the decision is still yours. This writes to your own filesystem; discovering a collision afterwards is not good enough.
  - **For a large h5ad it also stops a pointless round trip.** The file used to be written to a server temp file, streamed through the browser, and written again — to a directory you did not pick. It is now written once, where you asked.
  - **Downloading is still there, per format.** Streaming to the browser is the right thing when the backend is not on the machine you are sitting at, and `GET /api/export/h5ad` is a URL that works today, so neither was removed.
  - **Rejected: the native OS save sheet.** `showSaveFilePicker` is the most literally "typical" dialog and is Chrome/Edge only, so Safari and Firefox would have needed this path as their fallback regardless — two code paths for every export format, to reach the same place.
  - `composeSavePath` now takes the extension it should append rather than hardcoding `.pkl`, with a list meaning *append the first, accept any* so `.pickle` stays a valid pickle. There is deliberately no default: a silent fallback is exactly how an h5ad ends up named `.pkl`.
  - **`PyscnModal` was deliberately not refactored onto the shared picker**, and the spec records why: serving it would mean adding `footer` and `onError` props to a component that otherwise needs neither, which is evidence the two uses are not the same thing — and it has no UI tests to refactor against.
- **A deep path is readable, and you can filter the folder you are in (File → Load…).** Research data lives deep: a real path from this project's own test runs is eleven segments and 140 characters. The breadcrumb scrolled horizontally and anchored left, so what you saw was `/Users/pcahan/CahanLab Dro…` — and the one segment that matters, the folder you are actually in, was off the end. It now **elides the middle and never the ends**: the tail is where you are, the head is how you get back out, and the part in between is traversal nobody reads. Fixed height, no scrolling, and a `…` opens the rest in place. It also **says `Home` rather than `/Users/pcahan`** — the browser already knows your shortcuts, so a path underneath one is named in terms of it. `Home › … › xcell › h5ad_empty_removed › best_per_stage` in place of the full 140 characters.
  - A **filter box** narrows the current folder as you type, because the fastest way to a file whose folder you can already see is to type three letters of its name. Substring rather than prefix — dataset filenames carry their identity in the middle: a date, a stage, a sample id.
  - The path logic is a pure, tested module (`src/lib/pathCrumbs.ts`, 12 cases) rather than JSX arithmetic.
- **Filter Genes asks for a share of cells, not a count (Analyze → Preprocess → Filter Genes).** `Min cells` was absolute, so the same setting meant something different on 2,000 cells and on 200,000. It is now a percentage defaulting to **0.1%** — a gene has to appear in one cell per thousand — with the count it works out to shown beside the field, because that count is what scanpy is given and what the analysis record will say. The conversion happens in the UI so the recorded parameter, and the exported notebook, carry the exact number that ran.
  - **The config key was renamed to `min_cells_pct` on purpose.** `docs/config.example.yaml` shipped `min_cells: 3`, meaning three cells; under the same name that value would have been read as three *percent* — 6,000 cells on a 200,000-cell dataset. Renaming means an old key is ignored rather than silently reinterpreted. Update it to `min_cells_pct` to set your own default.
- **`injective` runs on datasets it used to refuse.** Solving the assignment exactly means holding the whole query × reference similarity matrix in memory, so the estimator capped itself and refused past it — a 50,000-cell query against a 20,000-spot reference is a billion entries. Above the size where the exact solver is affordable it now assigns over each cell's **128 best candidate spots** instead of every spot. A case that was refused outright — 15,000 cells against 30,000 spots, 450 M entries, 5.4 GB dense — completes in 6 seconds with every cell on its own spot.
  - **The approximation is invisible where it matters.** Measured on the E11.5 limb pair (2,683 × 9,773): the candidate solution's total similarity is **0.18% below** the exact optimum with **87% of cells on the identical spot**, and the Map quality panel cannot separate them — area 0.99 against 1.00, all 2,683 spots distinct either way, skin pattern +0.285 against +0.298 on a metric that moved between 0.285 and 0.365 across variants whose objective differed by 15%. Mean similarity, which is what the objective actually optimizes, converges to the exact value. The run reports `assignment: exact | candidate` and the modal says so outright, because a near-optimal answer must never be readable as an exact one.
  - **Feasibility had to be constructed, not hoped for.** A plain top-*c* candidate graph had **no full matching at all** on that pair for every *c* ≤ 64: many query cells rank the same well-recovered spots highest, so their candidate sets overlap and Hall's condition fails — which is the very pile-up `injective` exists to remove. Seeding the graph with a greedy injective assignment makes a full matching a theorem rather than luck, and the optimizer can only improve on it.
  - **Two construction traps worth naming**, both measured while building this. Assembling the sparse matrix with duplicate `(row, col)` pairs **sums** them, so every seed edge that is also a candidate had its cost doubled and the solver avoided exactly the edges it should prefer — 12% of the objective, presenting as a worse algorithm rather than a bug. And a stored cost of exactly zero reads as *"no edge"* to the matcher, which would silently delete the best edge in the graph.
  - **The old ceiling was also mis-documented.** It claimed 1e8 float32 entries was 400 MB; scipy converts its input to float64 internally, so the real peak was 12 bytes per entry (measured: +210 MB on top of a 105 MB array), or ~1.2 GB. The dense path is now capped by what already works — the limb pair runs dense today and still does, bit-identically.
  - **A second memory wall, fixed while there.** The similarity block was a fixed 2,048 rows regardless of reference size — 820 MB against a 100,000-spot reference, for *every* aggregation rather than only the assigning one. The chunk now shrinks so the block stays bounded.

### Fixed
- **A task that runs longer than five minutes is no longer reported as lost at the moment it succeeds.** The background-task reaper measured a result's age from the task's *creation*, so any run whose **runtime** exceeded the 300 s TTL was deleted from the registry at the first status poll after it finished — the UI got 404, showed *"Lost connection to task: Task not found"*, and never refreshed the schema, so the results that `apply_fn` had just written were invisible. Transport-aggregation Localize exceeds five minutes at real dataset sizes (reproduced at 20k × 40k cells / 22k shared genes: 397 s, applied successfully, reported lost), which is why that aggregation seemed to fail every long run while `weighted_mean` (~90 s) never did. Terminal tasks now stamp `finished_at` and the TTL runs from there.
- **When the backend restarts mid-task, the UI now says that, immediately.** The task registry lives in the backend process, and `uvicorn --reload` replaces that process on any `.py` edit — including edits made by a Claude session working in the repo, or a file-sync touch. Every poll after the restart can only 404, yet the poller burned three silent retries and then blamed the connection. - **`transport` — the first Localize estimator that fills the tissue *and* keeps the gradient (Analyze → Spatial → Localize).** Every other aggregation sits at one end of a single trade-off. On the E11.5 limb pair (2,683 cells against 9,773 spots), `weighted_mean` covers **8.6%** of the tissue with the epidermis at **−0.256** and the distal markers at **−0.532** — both inverted, placed where those populations are not — while `best_match` holds 49.6% of the area by putting all 2,683 cells onto **twenty-two spots**. Entropic optimal transport solves for all cells at once subject to the tissue being occupied, so it moves *along* that frontier instead of sitting at an end of it. Measured at the shipped default: **area 0.437 over 1,774 distinct spots, with all three marker patterns positive and both inversions reversed** — epidermis −0.256 → **+0.271**, distal −0.532 → **+0.353** — and axis fidelity better than `best_match` on both axes, including the proximal axis where `best_match` is itself inverted.
  - **ε is the dial, and it is measured in units the data cannot shift.** Sinkhorn forms exp(−C/ε), so ε trades against the *spread* of the cost matrix rather than its absolute scale; the transform and metric you pick move the effective ε across 3.5× while the useful tuning range spans only 2.5×. The preprocessing would otherwise move the dial further than the dial travels. The cost is normalized, so ε means the same thing under `none`+`cosine` as under `zscore`+`correlation`, and one default survives both.
  - **Which spread is the subtle part, and getting it wrong destroyed the map.** Entropic OT is invariant to `C_ij → C_ij + a_i + b_j` — both offsets are absorbed into the potentials, so neither can move the coupling. The first implementation divided by the global standard deviation, which counts them. On this pair the **column effect alone was 98% of the global spread** (0.0808 of 0.0827, against a double-centred 0.0134): reference spots that are better recovered and so similar to *everything*, the same artifact that makes `best_match` pile up. That inflated the scale **6.2×**, so every run converged in ten iterations to a near-uniform coupling and the map collapsed to 0.5% of the tissue at every ε tried. Double-centring before measuring the spread is the fix, and the test that asserts the coupling is unchanged under per-cell and per-spot offsets is the one that would have caught it.
  - **The default is ε=0.05, and 0.03 was rejected despite scoring higher.** 0.03 reaches area 0.477 with the best marker patterns in the sweep, and does not meet its convergence tolerance in 400 iterations (final marginal error 4.4e-3, 44× the tolerance). A default whose marginals were never satisfied would contradict the reference-side marginal that is the whole reason to use this method. `max_iterations` moves 200 → 300 alongside it, because at 200 the new default would not converge either. The full sweep is in `docs/superpowers/measurements/2026-08-11-transport-epsilon-sweep.md`.
  - **Pattern fidelity is not readable on a collapsed map**, and the sweep shows why: the epidermis scores **+0.783** at ε=2.0, the highest number in the table, on a map covering 0.4% of the tissue across 72 distinct spots — every cell falls in a handful of bins and the correlation measures almost nothing. Read pattern together with area, never alone.
  - **Log-domain always.** The naive kernel form does not fail on the kernel entries but on the scaling vectors, and it fails at exactly the small ε where this estimator is worth using — at ε=0.002 the kernel reaches exp(−1200) and flushes to exactly zero. One stable path is worth more than the 2–3× per-iteration saving of a form that breaks where it is needed.
  - **Convergence is measured on the row marginal, not the column.** The column potential is updated last, so immediately afterwards the column marginal holds to machine precision however far from converged the coupling is: measuring it reported 1.7e-15 on the second iteration and stopped there, with the rows still wrong by 5.7e-4. Only the un-enforced marginal carries information. Every run reports its iteration count and final marginal error, because a run that spent its budget has *not* satisfied the constraint that justifies the method.
  - **Confidence now comes from the posterior.** Each row of the coupling is a spatial posterior — the honest output for a cell that genuinely could be in several places — so confidence is that posterior's spatial spread, the same quantity the k-NN path already computes over its k neighbours. Row entropy was the alternative and is rejected: it is not in spatial units, so a transport run's confidence could not be read against any other run's, and comparing runs is what Map quality exists for.
  - **Dense while affordable, spatially-stratified subsample above it, and the run says which.** The limb pair is 26.2M entries and stays dense. Above the ceiling the reference is binned and sampled with at least one spot per occupied bin, because uniform sampling thins a sparse extremity in proportion to its density and the column marginal would then enforce occupancy of a tissue missing a limb. Runtime is 203 s at the default on that pair, as a cancellable background task with per-iteration progress.
  - **It is offered, not preferred.** `weighted_mean` remains the default aggregation; changing that needs its own evidence on more than one dataset. The composition assumption behind the reference-side marginal is stated in the panel rather than left implicit: forcing the tissue to be occupied asserts that the query's composition matches it, and dissociation biases which cell types survive.
  - Backend: `xcell/transport.py` (`normalize_cost`, `sinkhorn_log`, `barycentric_projection`, `posterior_spread`, `stratified_subsample`), 21 unit cases. Frontend: the ε control and its guidance in `LocalizeModal`, five new cases in `localizeAdvice`.
- **A Localize estimator that gives every cell its own spot, and a warning the default has earned (Analyze → Spatial → Localize).** Phase 1 made the failure measurable; this acts on what it measured. Two independent pieces.
  - **`injective` — best match solved as a set rather than one cell at a time.** `best_match` takes each cell's single best spot independently, so a spot that correlates well with everything — better recovered, less noisy — absorbs many cells. Optimal assignment maximizes total similarity subject to *distinct* spots, via `scipy.optimize.linear_sum_assignment`. On the E11.5 limb pair (2,683 cells, 9,773 spots): **2,683 distinct spots out of 2,683**, up from 1,522 for greedy, in about a second. The cost is a few percent of mean similarity.
  - **It is not better, it is elsewhere on the same frontier, and the UI says so.** Filling the tissue and carrying a gradient are the two ends of one trade-off. Measured on that pair: `weighted_mean` area **0.17** with the epidermis at **−0.16** — inverted — while any single-location estimator holds area **1.00** with the gradients gone. `injective` fixes pile-up, not placement; its axis correlations are greedy `best_match`'s to within noise. Presenting it as strictly better would be exactly the failure Phase 1 was built to prevent, so the panel, the guide and the Avoid list all state the trade rather than implying a winner.
  - **Off by default, and refused rather than fudged.** Injectivity asserts that the query's composition matches the tissue's; dissociation biases which cell types survive, so forcing one-to-one pushes over-represented types into locations they do not belong. It needs at least one spot per cell — the option is disabled when the query outnumbers the reference, and the same check runs in `prepare_localize` so an impossible run is a readable 400 rather than a background task that dies a minute in. It also materializes the whole query × reference similarity matrix, which the chunked top-k path never does, so there is an explicit size ceiling instead of an out-of-memory kill.
  - **The default's failure is now stated before the run, not after.** For every gene set curated in the Gene panel, `POST /api/localize/reference_geometry` asks the reference alone where the mean of that population's own positions falls. If the population forms a ring or hugs the tissue edge, that mean is a place none of its cells occupy — **the mean of a ring is its hole** — and `weighted mean` sends every query cell of the type there. On the limb reference: skin **0.88**, blood 0.70, cartilage 0.18, muscle 0.00. The modal names the ones at risk while the parameters are still being chosen.
  - **Two formulations were built and thrown away, both of which look right.** Counting how many of the cells around that mean are population *members* is correct in every case and far too noisy — 8 expected among 40 neighbours, so it fires on an ordinary scattered population about 1 seed in 60, and a user with a dozen gene sets would see a spurious warning most sessions. Scoring the *mean rank* of the tissue there fixes the variance and introduces a worse bug: it depends on how much tissue the population covers, saturating near 0.25 for a population covering a quarter of the reference, so the warning never fires. What ships compares the mean's distance from the population against the population's own spacing — scale-free, and blind to the background entirely.
  - **The real data corrected the design twice, and neither correction came from a test.** Taking a fixed top fraction as "the population" was silent on the very case it was built for: skin markers are detected in only 7% of limb spots, so the top 20% is mostly interior tissue with trace expression, the population fills the bud, and the risk reads 0.14 on a map already measured as inverted. Each fraction is now scored and the worst reported, with the fraction that produced it — at the top 2%, the epidermis proper, the same reference scores 0.88. Separately, averaging over 25 neighbours walks a quarter of the way around a thin band and hides its hole; at 5 a one-cell-wide perimeter scores 0.79 where 25 gives 0.38.

Frontend: `adviseParameters` moves to a pure, unit-tested `src/lib/localizeAdvice.ts` (17 cases, several asserting it stays *silent* — advice that fires on ordinary settings trains the user to ignore it).
- **Map quality — scoring a Localize map instead of eyeballing it (Analyze → Spatial → Localize).** On a real E11.5 mouse limb pair the default settings inverted the tissue's most basic anatomy — the epidermis, the outermost tissue in the embryo, was predicted into the middle of the bud — and nothing in the tool said so. The confidence score was working (mean 0.19 correctly reported that the matched neighbours were scattered), but "the map looks wrong" was not actionable: eight saved parameter variants existed on that dataset with no way to rank them. **Map quality** scores every predicted embedding in the query against the reference, so they can be compared rather than argued about.
  - **Four metrics, each answering a question a user actually asks.** *Spatial pattern fidelity* — does this cell type land where it lives? The headline number, and the one that catches the inversion: it goes **negative** when a type is placed where it is not, which is a different kind of wrong from merely weak. *Axis fidelity* — are the gradients real? Reported as "x of y possible" against what the reference itself achieves, because an attenuated correlation means nothing without its ceiling, and the direction is derived from the reference so the user never declares which way is distal. *Dispersion* — does the map fill the tissue, with cells pushed outside it counted separately, since a rescale can reach the right area by ejecting cells. *Occupancy* — distinct spots used, maximum on any one, and the effective number from the assignment entropy, which catches a better-recovered spot absorbing many cells even when the distinct count looks fine.
  - **Everything is rank-based, and not for style.** The reference is spot-resolved and the query is dissociated cells, so their expression scales are not comparable; and an estimator that shrinks the map changes the coordinate scale without changing what it claims. Ranking both sides makes every metric invariant to any monotone rescale — an affine rescale of the predictions provably cannot change a rank correlation, so a metric that moved under one would be measuring the wrong thing. That invariance is what makes maps from different settings comparable at all.
  - **One formulation had to be thrown away.** Comparing marker-*weighted* densities is the obvious approach and it is confounded: both maps then carry the same "where are there cells at all" signal, which dominates. Measured on synthetic geometry, two unrelated markers scored +0.33 and a fully inverted one only −0.07. Dividing the weighted sum by the cell count per bin isolates "is this marker high here", and the same three cases become +0.99 / −0.99 / ~0.

- **Localize — predict spatial coordinates for dissociated cells (Analyze → Spatial → Localize).** Load a spatial dataset into one slot and an scRNA-seq dataset into the other, and every cell in the scRNA-seq data gets a predicted position: its *k* nearest transcriptional neighbours among the spatially-resolved cells vote on where it came from. The result is a new embedding (`.obsm['X_spatial_pred']`), so the whole existing stack — colouring, contours, spatial neighbours, ligand-receptor — then applies to a dataset that never had coordinates. Parameters are all interpretable: *k*, the gene subset, the similarity metric, the expression transform, and how the neighbours' coordinates are combined. This is the first feature that spans two dataset slots.
  - **The failure mode it is built around.** Averaging the coordinates of *k* transcriptionally-similar cells is only meaningful if those cells are spatially co-located. A cell type dispersed through the tissue — immune cells, fibroblasts — has neighbours scattered everywhere, and their centroid lands in the middle of the tissue, possibly somewhere that type never occurs. A type sitting in two distant patches is worse: the mean lands squarely in the gap. Both produce a smooth, convincing, entirely wrong map, and nothing about the coordinate itself gives it away. So every prediction carries **two independent scores**, both written to `.obs` and neither optional: `_similarity` (does this cell resemble anything in the reference at all — a cell type absent from the spatial data is still placed *somewhere*) and `_confidence` (do its neighbours agree on a location — the weighted spatial spread of the *k* neighbours normalized by the reference tissue's own radius, so 1 means they sat on one spot and 0 means they were as scattered as the whole tissue). Cells below a chosen `min_confidence` get **NaN coordinates** rather than a fabricated point; the default places everything and flags it, because silently dropping cells is its own kind of lie.
  - **Aggregation.** `weighted_mean` (the classic estimator), `median` (robust to a few scattered neighbours), `best_match` (snaps to a real reference cell, so a prediction never lands somewhere the tissue does not exist) and `densest` — which averages only the tightest cluster among the neighbours. `densest` is the answer to bimodality: it lands the cell in one of the two patches rather than in the empty gap between them. It **cannot say which patch** — two patches sharing an expression program are indistinguishable to anything reading expression — and does not pretend to; on the bundled benchmark it picks correctly about half the time, which is why the default stays the mean and the confidence score (near zero for such cells either way) is what says not to trust the choice.
  - **Choosing which genes similarity is computed over.** A **Similarity basis** picker offers every shared gene, any boolean `.var` flag on the *reference* (`spatially_variable` from Spatial Autocorrelation, `highly_variable`, …), or any gene set curated in the Gene panel. The reference owns the choice because it is the dataset that can show which genes carry positional signal. The gene-overlap preview recomputes as you change it, so narrowing the basis immediately shows what it costs in shared genes. How much it helps depends on the panel: on whole-transcriptome data, restricting to spatially variable genes removes thousands of genes that say nothing about position; on an already-targeted panel, expect little change (measured on the bundled benchmark: 40 highly-variable genes score 32.7 against 33.0 for all 120).
  - **Guidance about the parameters, in the tool.** The panel raises warnings against the current selection rather than listing caveats nobody reads — `none` + `euclidean` across platforms (sequencing depth becomes the strongest signal), a *k* above a tenth of the reference (every prediction drifts to the tissue centre), `densest` with too few neighbours to cluster, `best_match` (where *k* no longer affects the coordinate, only the confidence score). A collapsible reference gives three concrete starting recipes and states each parameter's trade-off, including the one that matters most: a smoother map is what this method produces when it is failing, so tune against the accuracy check rather than against the picture.
  - **Cross-platform by default.** The transform is applied to each dataset *independently*, which is what removes platform-level per-gene capture efficiency: `zscore` (default), `rank` (Spearman-equivalent, robust to any monotone difference), `log1p`, `none`. Gene overlap is computed by **name** and reported with a severity band before anything runs — the same reasoning as the PySingleCellNet coverage check — and refused outright below ten shared genes, since a map from a handful of genes still looks smooth and means nothing. A multi-section reference is handled by assigning each cell the weighted-majority section among its neighbours and drawing coordinates only from that one, so a position is never averaged across the gap between cuts.
  - **Accuracy you can check before trusting it.** A **Check accuracy** button holds out a fifth of the *reference* and predicts it from the rest with the same parameters, where ground truth is exact. It reports median error next to **two baselines** — predicting the tissue centroid, and predicting at random — because an error reported alone is unfalsifiable: on a compact tissue the centroid baseline is deceptively strong, and the panel says so outright when the method fails to beat it. Also reported: the fraction landing within 5/10/25% of the tissue diameter, a structure correlation (do cells predicted near each other actually sit near each other?), a per-cell-type breakdown, and the correlation between confidence and actual error — the design's own falsification test, since a confidence score that does not predict error is decoration. The check is labelled as an upper bound, since both halves come from one platform and the real cross-platform mapping is worse.
  - **A benchmark with exact ground truth ships with it.** `toy_localize_spatial.h5ad` + `toy_localize_scrna.h5ad` (generator: `python -m xcell.data.generate_toy_localize`), a matched pair whose true coordinates are kept in `.obsm['spatial_true']`. The tissue is built to defeat the method: four region-restricted programs are the easy case, while `Immune` is dispersed with no positional signal, `Bipolar` sits in two distant patches sharing one program, and `Circulating` exists only in the query. The two files differ in depth, dropout and per-gene capture, so the transform matters the way it does across real platforms. Measured on it: median error **32.8** against a **66.7** centroid and **86.8** random baseline; per type, the four localizable programs land at 21–24 and the three unlocalizable ones at 64–79; confidence tracks error at r=**−0.66**; and of 900 query cells, **386** score below 0.2 confidence where 388 are unlocalizable by construction — the score identifies almost exactly the right cells.
  - Backend: new pure module `backend/xcell/localize.py` (projection, four aggregations, `evaluate_localization`, `cross_validate_localization`); `spatial_reference_bundle` on the reference adaptor and `prepare_localize` / `prepare_localize_cross_validation` / `evaluate_localization` on the query; `GET /localize/suggest` + `POST /localize/prepare` / `/cross_validate` / `/evaluate`. Frontend `LocalizeModal`. Because two datasets are involved, the reference exports plain arrays rather than letting a route reach into its AnnData.
- **Analysis record — export a GUI session as a runnable Jupyter notebook or Markdown (File → Analysis record…).** Reproducibility is the standing objection to GUI analysis: you click through thirty operations and nothing about that path is publishable, re-runnable, or legible six months later. Every mutating operation is now recorded — the load, its parameters, its result — and the record exports as a notebook whose code cells re-execute the analysis, or as a Markdown methods supplement. Steps carry the user's own annotations plus a generated one-line summary built from the real numbers (*"Leiden clustering at resolution 1.0 → 12 clusters in `.obs['leiden']`"*), and figures captured from the plot (**◧ Figure**) become inline outputs in the notebook and linked PNGs beside the Markdown.
  - **The document says how much of itself actually re-runs.** The tempting version of this feature emits a tidy notebook that *looks* authoritative; that version is worse than nothing, because a methods supplement describing an analysis nobody ran is a citation-grade error. So each step carries a **fidelity**: `exact` — the emitted line is the library call the adaptor really makes (`run_normalize_total` with no active selection literally executes `sc.pp.normalize_total(self.adata, **kwargs)`, which is why it earns the label); `xcell` — reproducible only by calling xcell's own Python API, which the notebook sets up by wrapping the AnnData in a `DataAdaptor`, including a runner for the two-phase `prepare_*` operations; `manual` — described in prose and not pretended to be code. The header states the split in numbers, and an action with no translation still exports as prose with its parameters rather than vanishing. A test scans `adaptor.py` for every `_log_action` name and fails if any lacks a translation, so a new operation cannot silently degrade an export.
  - **Operations that ran on a cell selection say so.** Ten adaptor methods accept `active_cell_indices` and none of them recorded it, so Leiden on a 4,000-cell lasso was logged indistinguishably from Leiden on all 40,000. The selection is now recorded (and preserved verbatim, up to 50,000 indices, in a `_selections.json` sidecar) and every affected step is flagged in the panel and in the exported document. We deliberately do **not** generate subset + write-back code: each of those methods has different write-back semantics — UMAP writes NaN for inactive cells, Leiden writes `'unassigned'`, `normalize_total` splices sparse data rows — and generated code that is subtly wrong is exactly the failure this feature exists to prevent. The emitted call runs on the whole dataset and says as much.
  - **Recording is always on; what you control is the report.** A record button users forget to press loses the analysis outright, and logging already cost nothing, so the recorder accumulates from load. **Start report here** marks where the story begins without discarding anything earlier.
  - **The record travels with the data.** It is written into `uns['xcell_analysis_record']` as a JSON string (h5ad copes badly with deeply nested heterogeneous dicts) minus figure payloads, so an exported `.h5ad` carries its own provenance and re-opening it continues the history rather than starting a second one. Export writes server-side into a folder you pick with the file browser — a notebook has to live next to the data to re-read it.
  - **Sixteen operations that recorded nothing now do:** label renames and merges, hand-painted annotation, QC metrics, differential expression, both gene-set scorers, the `.var`-side edits (gene renaming, boolean flags, per-pattern and per-species count sums, identifier swap), obs-derived embeddings, and the ligand-receptor analysis itself — `finalize_ligrec` logged only the `.obs` columns it wrote, never the radius, permutations or threshold that produced them. The load is recorded too, distinguishing h5ad / 10x h5 / 10x mtx / in-memory, so a dataset built in memory is reported as not reproducible instead of pretending a file exists.
  - Backend: new pure modules `backend/xcell/analysis_record.py` (the model and its `uns` round-trip), `codegen.py` (one `ActionSpec` per action: label, summary, code, fidelity) and `notebook_export.py` (nbformat-4 and Markdown emitters); `/api/record` routes for reading, annotating, marking and exporting. Frontend `AnalysisRecordPanel`, plus figure capture on the plot which re-renders the stored snapshot points into an offscreen 2D canvas — deck.gl does not set `preserveDrawingBuffer`, so reading back the live WebGL canvas is not reliable.
- **Cell type classification with PySingleCellNet (toolbar → Cell Typing).** An optional integration with [PySingleCellNet](https://github.com/CahanLab/PySingleCellNet), which classifies cells by voting a random forest over *top-scoring gene pairs* ("is gene A above gene B in this cell?"). Two tabs. **Classify** takes a pickled classifier, and before running anything reports what it is (classes, gene pairs, trees, training parameters) and — the part that matters — **how much of its gene set this dataset actually has**. PySCN reindexes a query onto the classifier's genes with `fill_value=0`, so missing genes silently become zeros and a badly-matched query still returns confident-looking scores; coverage is shown with a severity band (ok / warn / error) and the missing symbols listed. A pure `ACTB`/`Actb` casing mismatch is detected as such and offers a one-click case-insensitive match rather than reporting 0% overlap. **Train** builds a classifier from a categorical `.obs` column — balancing cells per type, normalizing, and selecting HVGs on a private copy, so the loaded dataset is never modified — writes the pickle, and hands it straight to the Classify tab. Both run as cancellable background tasks with live progress.
  - Results land in the slots xcell already knows how to draw: `<key>_class_argmax` (the call, a categorical whose colors come from the classifier's own `ctColors` via `uns['<column>_colors']`), `<key>_class_score` (the winning vote proportion, i.e. the call's confidence), and optionally `<key>_class_type` — **Singular** / **Ambiguous** / **None** / **Rand**, following PySCN's `categorize_classification` rules with self-calibrated per-class thresholds (`comp_ct_thresh`). PySCN splits the multi-class case into *Intermediate* and *Hybrid* using a cell-type relatedness graph xcell does not have, so those cells are reported as **Ambiguous** rather than guessed at. The full cells × classes score matrix goes to `.obsm['<key>_score']` and is registered in `uns['xcell_score_matrices']`, so the existing **◈ score matrix** pills in the Genes panel colour by any single class and the embedding picker can plot two classes against each other. The run is recorded in `uns['pyscn'][<key>]`; re-running under a different prefix keeps both results side by side.
  - **Training adapts to the scale the reference is already on.** Many public references are distributed *only* as log-normalized values, and running `normalize_total` + `log1p` over those again yields `log1p(scale(log1p(x)))`. Training now detects the source scale (via the expression-scale detection above) and applies only the preprocessing still owed — everything for raw counts, `log1p` alone for linear-normalized data, nothing for already-logged data — picking the HVG flavor to match, and never labelling a log-valued matrix as `counts` for `seurat_v3` to consume. A **Scale of that matrix** dropdown shows what was detected and overrides it, since detection is a heuristic; the result panel states exactly what was applied. A z-scored source is refused outright. Worth being precise about the blast radius, which is smaller than it looks: the top-scoring-pair features are *bit-identical* under a double log, because `normalize_total` and `log1p` are per-cell monotone and the transform only compares two genes within one cell (pinned by a test). What the double transform corrupts is gene *selection* — `rank_genes_groups`, the PCA/dendrogram used to find similar cell types, and HVG.
  - **The package is optional.** Nothing imports it at module scope; when it is absent the panel shows install instructions instead of failing, and *classifier inspection still works* (it only needs scikit-learn) so a classifier can be checked against the data before committing to the install. `pixi install -e pyscn` provides it reproducibly.
  - Two failure modes of the upstream library are handled rather than passed through. xcell narrows the query to exactly the classifier's genes before handing it over, so the dense intermediate PySCN builds is proportional to the classifier (a few hundred columns) rather than to the dataset — the difference between megabytes and tens of gigabytes on a large query — and prediction is chunked over cells. And because PySCN encodes each gene pair as the string `geneA_geneB` and decodes it with `split("_")`, **gene symbols containing an underscore cannot be represented**: training now excludes them and says how many, refuses with an explanation when too few remain, and loading a classifier trained on such symbols fails with a clear message instead of an opaque pandas `KeyError` at prediction time.
  - Backend: new module `backend/xcell/pyscn.py`, `pyscn_status` / `pyscn_inspect_classifier` / `prepare_pyscn_classify` / `prepare_pyscn_train` on the adaptor, and `GET /pyscn/status` + `POST /pyscn/inspect_classifier` + `/pyscn/classify` + `/pyscn/train` routes; frontend `PyscnModal`.
- **Expression scale detection — "is this layer raw counts or already normalized?"** Every readable matrix (`.X` and each `adata.layers` key) is now classified from its own values as **raw counts**, **normalized (linear)**, **log-normalized**, **log-transformed**, **scaled / z-scored**, or **binary**. Files arrive from collaborators and public repositories with no record of what was done to them, and guessing wrong is not cosmetic: `normalize_total` on already-normalized data is a no-op that looks fine, UCell ranks and PySCN's gene-pair transform assume a per-cell monotone scale, and z-scored input breaks anything expecting non-negative values. The signals, in the order they discriminate: negatives (only centering produces them), integrality (counts are integers), constant row sums (`normalize_total` fixes the library size), constant `expm1` row sums (the same check after undoing `log1p`, which identifies the scanpy-default scale), and dynamic range as a fallback for the common case where genes were subset after normalizing and the row-sum signal is gone. Alongside the inference it reports **recorded provenance**, which is fact rather than guess: `adata.uns['log1p']` from scanpy, the `counts` layer xcell snapshots at load time, and xcell's own `normalize_total` / `log1p` / `scale` / `smooth` history.
  - Surfaced unobtrusively: the verdict rides inline in the existing **Source** dropdown labels (`.X (default) — log-normalized`), and a 16px **ⓘ** opens a popover with the confidence level, the reasoning in plain language, the provenance, and the underlying statistics. The Source row now renders for single-`.X` datasets too, which need the answer just as much. The UCell and Cell Typing dialogs reuse the badge next to their layer pickers and warn outright when a z-scored layer is selected, since both are rank-based and would produce silently meaningless results.
  - Backend: new module `backend/xcell/layer_scale.py`; `list_layers()` attaches a `scale` block to each entry, so `GET /scanpy/layers` carries it with no new endpoint. Frontend `LayerScaleInfo`.
- **Score matrices written by other tools are readable.** `.obsm` entries stored as labelled pandas DataFrames — how PySingleCellNet writes `SCN_score`, among others — now expose their own column names to the schema, colouring, and embedding pickers, so an `.h5ad` classified elsewhere can be explored in xcell without conversion.
- **Ligand-Receptor spatial signaling (Analyze → Spatial → Ligand-Receptor).** A from-scratch NumPy/SciPy port of the core LRscore + permutation statistics of [CytoSignal](https://github.com/welch-lab/CytoSignal) (velocity/dynamics omitted). For each cell and each L-R interaction it imputes ligand expression over a spatial neighborhood — a Gaussian ε-ball for **diffusion**-dependent (secreted) ligands, direct **Delaunay** neighbors for **contact**-dependent (membrane) ligands — multiplies it by the cell's own receptor, spatially smooths the score, and tests significance against a spatial permutation null (shuffle the ligand neighborhood, keep each cell's receptor) with a BH-adjusted per-cell p-value. The tool ranks interactions by number of significant cells; pick any to write its per-cell score as a continuous `.obs` column (`LR_<ligand>_to_<receptor>`) and visualize it on the embedding. Parameters (diffusion radius, permutations, min cells/gene) are prefilled from the data with inline tips, and the run shows a **live progress bar** (permutation count, % and elapsed/ETA). The full per-cell score + significance matrices are persisted to the dataset (**`.obsm['lrscore']`** / `['lrscore_significant']`, with metadata in `.uns['lrscore']`) — `.obsm` is the correct cell×interaction home (`.obsp` is cell×cell). Because results persist, **re-opening the tool restores the ranked table so you can visualize different interactions without re-running**; only changing scoring parameters (radius, permutations, …) requires a recompute. **Section-aware**: an optional Section column keeps neighborhoods *and the permutation null* within section (no signaling across the gap between tissue sections). **Gene subset**: optionally restrict eligible genes to a boolean `.var` column (e.g. `highly_variable` / `spatially_variable`); off by default. The scoring engine reduces the expression matrix to just the genes used by the candidate pairs and computes the (permutation-invariant) receptor side once — roughly a **35×** speedup on a 2,000-gene panel (and more for whole-transcriptome data). It builds its own Gaussian/Delaunay neighbor graphs each run and does not reuse the Spatial Neighbors graph. Ships a bundled ligand-receptor database (`backend/xcell/data/lr_pairs.csv`, 2508 pairs distilled from CellPhoneDB v5 with the diffusion/contact split and multi-subunit complexes preserved; rebuild with `python -m xcell.data.build_lr_db`). The database uses human (UPPERCASE) symbols but is matched **case-insensitively** to the dataset's gene names, so it works on mouse data (`Pdgfb` → `PDGFB`) — mirroring CytoSignal's uppercase-match; written columns use the dataset's actual gene names. (This is a heuristic; a proper mouse→human ortholog table is planned — see `docs/ROADMAP.md`.) and a synthetic test dataset with known planted signaling (`toy_spatial_ligrec.h5ad`; generator `generate_toy_ligrec.py`). Backend: new pure module `backend/xcell/ligrec.py`, two-phase `prepare_ligrec` (cancellable background task) / `finalize_ligrec` on the adaptor, `GET /scanpy/ligrec/suggest` + `POST /scanpy/ligrec/prepare` + `/finalize` routes; frontend `LigRecModal`.
- **Refine a category with subcluster labels (Cells → Categorical → ⋯ → Refine with subcluster labels…).** After masking some cells and subclustering the rest (which leaves the masked cells `unassigned` in a new column), fold those subcluster labels back into a parent annotation: every cell with a real subcluster label takes it (optionally renamed — prefix with the parent label, e.g. `Mesen.0`, use as-is, or a custom prefix), while cells the subcluster left unassigned keep their parent label. Writes a new column or overwrites the parent in place; surviving parent labels keep their colors. Backend: `transfer_obs_labels` on the adaptor + `POST /obs/transfer_labels`; frontend `TransferLabelsModal`.
- **Categorical labels overlaid on the embedding (Cells → Categorical → ⋯ → Show labels on plot).** Toggle category names rendered at each cluster's centroid (robust median position) directly on the embedding, with a dark halo for legibility. Turning it on also colors by that column so the labels match the clusters.

### Fixed
- **Localize could never pick a spatial reference.** The modal seeded its reference slot with the literal string `'secondary'` and asked the server for the list of usable slots *with that guess attached*. But the list only comes back from a call naming a **valid** reference, and both natural arrangements return 400 — `?reference=secondary` when the coordinates are in primary ("no spatial coordinates"), and `?reference=secondary&dataset=secondary` when the user makes the scRNA-seq active ("the reference must be a different dataset"). Both 400s were swallowed deliberately, since a slot without coordinates is a normal state rather than an error, and the handler returned before `setRefs` — so the list stayed empty, the tool reported *"No loaded dataset has spatial coordinates"* while a perfectly good one was loaded, and the picker that would have corrected the guess was itself built from the list that never arrived. A bootstrap deadlock: switching the active dataset produced a different 400 and the same message. The slot list is now fetched with no reference at all, which the route answers unconditionally (it builds the list before validating a reference), so the picker always populates.
  - **Roles no longer depend on which dataset is active.** Localize is the one feature spanning two slots, and it inferred the query from the active one — punishing the obvious workflow of loading the spatial data, looking at it, and then trying to map onto it. The dataset holding coordinates is now the reference and the other is the query, whichever is being viewed. The modal states both, plus which dataset the predictions get written into, and offers a swap when both carry coordinates. The role logic is a pure function (`lib/localizeRoles.ts`) with its own tests, including one asserting the answer does not move when the active slot changes.
- **Neighbors on a cell selection failed for every dataset.** `run_neighbors` builds a throwaway AnnData holding only the selected cells' `.obsm` representation, deliberately with no `.X`. scanpy's `use_rep=None` default resolves the representation from `adata.n_vars`, which on that object is 0, so it fell through to `.X` and raised on `None`. The whole sequence a user performs — lasso a subset, PCA, Neighbors, Leiden — could not complete. The representation is now named explicitly.
- **An embedding containing NaN returned a 500.** NaN is a legitimate value there: `run_pca` and `run_umap` on a cell selection leave inactive cells NaN, and Localize leaves unplaceable cells NaN rather than fabricating a position. But starlette serializes strictly, so `GET /api/embedding/<name>` raised *"Out of range float values are not JSON compliant"* and the result of a subset UMAP could not be displayed at all. Non-finite coordinates now cross the wire as `null`.
- **Figure builder: highlighted cells no longer obscured by overlapping low-expression cells.** When a figure panel colored cells by expression (or a numeric/bivariate source) *and* the highlight overlay was on, an overlapping non-highlighted zero/low-expression cell could be drawn over a highlighted cell and hide its color — visible when zoomed out (e.g. purple min-expression spots covering brown cartilage-highlighted spots). `FigurePanel` ordered cells by expression value only; it now applies a second stable sort by max highlight weight (matching the main Embedding view), so highlighted cells render on top. Applies to the PNG export too.

First load takes ~1–2 min (it reads ~32k HDF5 gene slices); the result is cached as a `<name>.xcell.square_008um.h5ad` next to the source file (reused while newer than the source; falls back to a temp dir if the source dir is read-only), so subsequent loads are instant. For the Visium HD Mouse Embryo sample this yields 344,021 bins × 32,285 genes. Bin size is a parameter (`bin_size=8` default; 16 µm also supported) but the load route currently hardcodes 8 µm — a load-time selector is future work.

### Fixed

Minimal reproducer kept at `frontend/repro.html` (served at `/repro.html` by the dev server) — use it to verify if any future deck.gl bump fixes this upstream so the workaround can be removed.

### Fixed
- Expression coloring errors (e.g., "Gene not found") no longer block the scatter plot. The error appears as a dismissable toast that auto-clears after 5 seconds, and the color mode resets so the app remains usable.
- When a dataset is loaded with no embeddings, the message now says to use Scanpy to create embeddings, instead of the misleading "No data loaded" message.
- Cell Panel now properly refreshes when switching between datasets or loading a new dataset
- Support for loading `.rds` files containing Seurat objects. Requires R and the Seurat/SeuratDisk R packages to be installed. RDS files are automatically converted to h5ad format on load.
- Load 10x Genomics Cell Ranger `.h5` files in addition to `.h5ad` files. The file browser now shows both formats, and the Load modal accepts either.
- Gene Neighbors basis selection: choose between gene PCA embeddings or raw expression as the basis for computing gene-gene neighbors. When using expression basis, optional gene subset filtering and z-score scaling are available. This lets you compare PCA-based and expression-based gene similarity results.
- Quilt mode undo: after rearranging cells in quilt mode, click the "Undo" button or press Ctrl/Cmd+Z to revert the last transform. Supports multiple levels of undo within a quilt session. The undo stack resets when exiting and re-entering quilt mode.
- Quilt mode: a new interaction mode for rearranging tissue pieces in spatial transcriptomics data. Click "Quilt" in the toolbar, lasso a group of cells, then drag to translate, shift+drag to rotate, or use flip buttons to reposition the selected patch. Press Escape to re-select, or Escape again to exit. Transforms persist in h5ad export.
- Side-by-side dual scatter plot view: click "Split" in the toolbar to view both primary and secondary datasets simultaneously. Click a plot to make it the active dataset. Each plot has independent pan/zoom, its own embedding selector, and its own legend. Interaction tools (lasso, draw, adjust) work on whichever plot you click. Gene and gene set coloring applies to both plots simultaneously.
- Embeddings created by Scanpy (PCA, UMAP) are now automatically selected for viewing, even when the dataset had no embeddings initially.
- Backend multi-dataset support: load multiple datasets into named slots (`primary`, `secondary`, etc.). All API endpoints accept an optional `?dataset=` query parameter. New `GET /datasets` and `DELETE /datasets/{slot}` endpoints for managing loaded datasets. Existing single-dataset usage is unchanged.
- Dataset slot selector in Load modal — load a second h5ad file into the Secondary slot without losing the Primary dataset.
- Dataset switcher dropdown in header toolbar (appears when two datasets are loaded) — switch between primary and secondary views seamlessly.
- Contourize spatial analysis: assign cells to spatial expression contour levels based on a gene set. Select genes in the Gene Panel, open Scanpy Modal > Spatial Analysis > Contourize, configure smoothing and contour levels, and run. Creates a new categorical obs column that can be used for coloring and downstream analysis.
- One-vs-rest marker gene analysis: click "Markers" on any categorical column in the Cell Panel to identify marker genes for each group using Wilcoxon rank-sum test. Select groups, set top N genes, and optionally apply fold-change and expression fraction filters. Results can be added as gene sets to the new "Marker Genes" category in the Gene Panel.
- Additive lasso selection: hold Shift while drawing multiple lasso shapes to select non-adjacent groups of cells without losing the previous selection.
- Embedding rotation and reflection controls ("Adjust" interaction mode): shift+drag to rotate, flip X/Y buttons. Transforms modify adata.obsm in place and persist in h5ad export.
- JSON import support in Import Gene Lists modal (`.json` files round-trip with export).
- Preferred embedding auto-selection on dataset load: spatial > umap > pca (case-insensitive substring match).
